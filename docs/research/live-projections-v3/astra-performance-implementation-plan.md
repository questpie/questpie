## Slice 1: make frame microbatch adoption transaction-safe

The candidate [fence store](../../../packages/questpie/src/server/modules/core/integrated/realtime/channel-authority-fence.ts) locks the channel coordinator first, then sorted unique subjects, and compares **each attempt's** expected generation. Missing subjects reject; mismatches refuse admission; callback failures are isolated. The [ledger](../../../packages/questpie/src/server/modules/core/integrated/realtime/channel-event-ledger.ts) seals at most 64 attempts before acquisition, permits two active batches globally and one per channel, and rotates busy channels. Later arrivals and busy-sink retries require new admissions. These are appropriate minimal mechanics; do not batch policy callbacks, provider installation, or arbitrary SQL publications.

Normal owned-transaction settlement occurs after commit. Existing per-binding drain serialization and oldest-frame retry preserve order; batch order is not a new cross-subscriber delivery guarantee. PostgreSQL holds row locks through transaction completion, which is why transaction ownership matters. See [PostgreSQL locking](https://www.postgresql.org/docs/17/explicit-locking.html).

**Fix before adoption:**

- Ambient fallback is not commit-safe. `admitLocalFrame()` calls generic admission when `getCurrentTransaction()` exists, but [withTransaction](../../../packages/questpie/src/server/collection/crud/shared/transaction.ts) reuses that transaction. The subsequent sink call therefore can occur before outer commit, while fences remain locked. The candidate ambient test actually allows this. This is inherited behavior, not a new batching-only defect. Reject frame delivery under an ambient transaction as the smallest fail-closed rule, or move the owning drain to an explicit after-commit entry point. Never await an after-commit delivery promise inside the transaction it depends on. Guard direct batch entry too; batching must own its transaction.
- `publish()` currently mutates shared `subscription.authorityGeneration` before commit, although the comment says results remain private. Commit rejection prevents this caller's sink write but does not undo that mutation. Make the frame comparison produce attempt-local state; publish remembered binding state only after successful commit, with a lifecycle/version check so a late result cannot overwrite newer reconciliation. Do not move sink work into the publication callback.
- Closed bindings remain in the pending admission queue, and publication does not check activity. Post-await activity checking prevents their sink invocation, but canceled attempts still consume SQL and retain closures. Remove or skip canceled attempts before sealing; check binding lifetime again after commit. Add a finite pending-admission limit and explicit overflow behavior. Two active transactions do not bound the waiting map across unlimited bindings.

Distinguish **logical admission** from **physical sink enqueue**. A frame admitted before a cut may reach transport afterward; a `busy` result grants no reusable admission. The current post-commit closed check helps, but cannot retract bytes an arbitrary sink has already accepted. Preserve that documented boundary; an enqueue-time hard cut would require a separate sink cancellation/generation contract. No slow reader may hold the database fence.

The [candidate unit tests](../../../packages/questpie/test/units/channel-frame-admission.test.ts) already describe exact subjects, 65-attempt splitting, two-channel concurrency, sealed arrivals, retry order, and failed commit without output. Extend them with outer rollback/no sink, close while awaiting commit, commit failure after a generation change, and reconciliation overtaking publication. Mock SQL tests cannot prove concurrent PostgreSQL lock behavior; retain that distinction in verification.

## Slice 2: keep arbitrary route LIVE isolated

The [scheduler](../../../packages/questpie/src/server/modules/core/integrated/realtime/refresh-scheduler.ts) intentionally appends a random group suffix to coherent subscriptions. Removing it is unsafe: the group owns one compute closure, authority epoch, invalidation callback, topic envelope, and cached frame. Legacy provider rebinding does not supply per-binding authorization.

[subscribeRouteQuery](../../../packages/questpie/src/server/adapters/routes/realtime.ts) refreshes verified identity on each evaluation and checks identity continuity and agent expiry. The [query executor](../../../packages/questpie/src/server/routes/execute.ts) then owns one read-only repeatable-read transaction containing watermark, request-derived facts, access, handler reads, and output validation. Reusing another evaluation's data after authorization in a different snapshot breaks that coherence. [PostgreSQL repeatable-read semantics](https://www.postgresql.org/docs/17/transaction-iso.html#XACT-REPEATABLE-READ) explain why equal input or watermark strings do not establish shared transaction identity.

**Recommendation: reject full-route compute sharing under the existing interface.** Tenant/role keys, identical dependencies, and a cached permission yes/no cannot establish equivalent output. Arbitrary handlers, request headers, services, field access, afterRead hooks, clocks, and output transforms remain observable. Same principal alone is insufficient.

The smallest honest future opt-in is a separate **pure data computation** contract, not an `accessCacheKey` on arbitrary handlers. A sealed cohort would require independently refreshed credentials for every binding; separate per-binding context facts and authorization within one owned snapshot; a narrowly supplied immutable input/data interface for the shared computation; and independent per-binding rendering/output validation. Only computation explicitly invariant across those verified bindings could be reused. System-mode fact services must not become another binding's handler services. This is a new interface, not a small scheduler-key patch.

Any such opt-in must define complete data and authority dependencies, including app facts and transitive hook/relationship reads; external facts need an explicit freshness contract. [Dependency declarations](../../../packages/questpie/src/server/routes/live.ts) validate shapes and collections, not completeness. Late arrivals cannot inherit a cohort's admission. Cancellation must detach only the canceled binding, discard its late callback/output, and keep unrelated consumers alive. Authority changes must purge each binding's buffered output; reconnect must perform fresh authorization before adoption. Retain the current [output-gate generations](../../../packages/questpie/src/server/modules/core/integrated/realtime/edge-session.ts) and snapshot-writer purge semantics. No automatic graph/planner is warranted.

## Slice 3: reuse the serialized payload within one refresh

`refresh()` first calls `stringifyCompatibleTypedEventWire({ data })` for hashing, then `encodeSseEvent()` serializes the original data again. The [typed serializer](../../../packages/questpie/src/shared/typed-wire.ts) itself performs stringify, parse, and Date-path traversal. This duplicated traversal is present now.

Prepare the compatible `{ data }` wire object once; hash its canonical serialized representation and build the snapshot envelope from that already-normalized payload and its Date metadata. Keep `data` at the same path, and avoid applying the reserved-key serializer twice. Reuse the existing SSE framing format. Preserve undefined/array/Date behavior, custom `toJSON` and getter semantics, errors, payload-size checks, and suppression with fresh up-to-date markers. Treat evaluating a stateful serializer once instead of twice as an explicit behavioral correction. Keep epoch/disposal checks after asynchronous hashing. Countertests should compare decoded wire output, Date-versus-string distinctions, unchanged-output markers, and an authority wake during hashing.

## Slice 4: remove canceled work and bound each existing class

The scheduler already coalesces refreshes and clears pre-start coherent wakes when the compute slot opens. Do not advertise those as new work. It has ten compute slots and a 1,024-entry waiting queue, but queued closures are not removable on disposal. Introduce cancellation-aware queue entries, with a disposed check before invoking compute. Preserve a dirty wake arriving after snapshot start; a maximum sequence alone does not prove transaction visibility coverage.

Separately, [SseLatestSnapshotWriter](../../../packages/questpie/src/server/modules/core/integrated/realtime/sse-client-transport.ts) bounds busy-result storage, but its serialized promise chain retains every queued `write` closure before that accounting. Coalesce unsent latest snapshots per topic at enqueue, accounting bytes immediately and preserving remove-generation fences. Never coalesce ordered durable frames. Preserve final-state coverage and keep errors/up-to-date markers from replacing a data snapshot the client has never received.

If fairness is needed, classify existing coherent refresh and legacy/delta compute work under one aggregate limit with bounded queues and fair service. Authority invalidation/purge stays synchronous, outside those queues. The two frame-batch slots are a separate class; they do not bound authorization reads or all pool use. Avoid adding concurrency or promising reserved database capacity. Countertest a saturated class, cancellation, FIFO durable delivery, and eventual latest-state progress.

## Slice 5: avoid eager services without sharing privileged scopes

[extractAppServices](../../../packages/questpie/src/server/config/app-context.ts) resolves every registered service eagerly. [resolveContextExtensions](../../../packages/questpie/src/server/config/questpie.ts) creates a fresh **system-mode** service scope, while query execution owns a separate user-mode scope. Thus request-scoped constructors can run in both, even when unused. Their separation is intentional: merging name-keyed caches could reuse privileged services.

A narrow follow-up is lazy resolution inside the nested `services` namespace, preserving names, enumeration, dependencies, disposal, and scope lifetime. Top-level injected services need separate treatment because spreading getters resolves them. First decide whether eager constructor side effects are contractual; do not silently change that behavior. [RequestScope](../../../packages/questpie/src/server/config/request-scope.ts) already memoizes instances, not query results. Application-owned immutable raw facts may be computed once and carried into access/handler work within the same evaluation; do not introduce a framework ACL cache. HTTP query context deferral and LIVE snapshot fact derivation are already fixed, not opportunities to claim again.

## First implementation and remaining decisions

Start with slice 1's owned-transaction boundary and cancellation/commit countertests, then retain the bounded frame batch. That fits the owner's performance authorization without another approval cycle. Follow with the single-refresh payload reuse; keep scheduling and service lifecycle changes independently reviewable.

Unresolved interface choices are hard enqueue-time cuts versus logical admission, admission-overflow policy, lazy service initialization semantics, and whether a restricted pure-compute opt-in is worth supporting. Leave arbitrary route sharing disabled meanwhile. AP's refetch-to-LIVE migration, eligible-row acquisition, and commands/MCP business equivalence remain AP-owner work; framework authorization caching cannot solve them.
