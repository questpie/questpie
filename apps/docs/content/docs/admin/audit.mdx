Someone changed a price last week and nobody remembers who. That is the
question this page answers. Add one module and every write starts landing in a
collection you can read like any other.

## Turn it on

```ts title="src/questpie/server/modules.ts"
import { adminModule } from "@questpie/admin/modules/admin";
import { auditModule } from "@questpie/admin/modules/audit";

export default [adminModule, auditModule] as const;
```

```bash
questpie generate   # registers admin_audit_log and a cleanup job
questpie push       # creates the table in your dev database
```

That is the whole setup. Nothing has to opt in. The module registers app-level
hooks, so they fire on every collection and every global at once.

`adminModule` is a separate module. Add it too and the log gets a sidebar item
under Administration, showing a read-only list of title, user and date.

The module also contributes a typed `config/audit.ts` convention. Generate once
after adding it, then choose delivery and retention explicitly when the defaults
do not fit your risk model.

```ts title="src/questpie/server/config/audit.ts"
import { audit } from "#questpie/factories";

export default audit({
	delivery: "required",
	retention: {
		days: 365,
		legalHold: async (event) => isHeld(event.id),
	},
	sink: {
		append: async (event) => immutableArchive.append(event),
	},
});
```

## What lands in the log

| `action`     | Written when                                          |
| ------------ | ----------------------------------------------------- |
| `create`     | A row is created.                                     |
| `update`     | A row changes. No changed field means no entry.       |
| `delete`     | A row is deleted, soft or hard.                       |
| `purge`      | A soft-deleted row is purged for good.                |
| `transition` | A record or a global moves to another workflow stage. |

Globals record `update` and `transition` only. A global has no create and no
delete.

Bulk writes are not one entry. `updateMany` and `deleteMany` run the write
hooks once per row, so a hundred rows write a hundred entries.

### Purge is deliberately thin

A purge entry keeps the action, the id and the actor. Its `resourceLabel` and
`changes` are both null. The point of a purge is that the row is gone. The
audit trail must not end up holding the last copy of it.

### Delivery is a policy

`delivery` defaults to `"best-effort"`. A persistence or sink failure writes a
structured error through `ctx.logger`, while the protected mutation still
commits. With `"required"`, the failure is rethrown inside the mutation
transaction, so the mutation and audit row roll back together. The same choice
controls cleanup failures: best effort logs; required makes the job fail.

Required delivery improves consistency with the database record, but an
external sink is outside that database transaction. A sink may receive an event
before a later transaction failure, and QUESTPIE does not retry or deduplicate
delivery. Make `append()` idempotent on the canonical event `id`.

## The row

`admin_audit_log` is an ordinary collection with `timestamps: true`, so
`createdAt` is when it happened.

| Field                | Holds                                                                  |
| -------------------- | ---------------------------------------------------------------------- |
| `action`             | One of the five above, or whatever a custom entry passed.              |
| `resourceType`       | `collection` or `global`. A custom entry may say anything.             |
| `resource`           | The key the resource has on `app.collections` or `app.globals`.        |
| `resourceId`         | The row id. Null for a global.                                         |
| `resourceLabel`      | The row's own label, cut to 200 characters.                            |
| `userId`, `userName` | The actor.                                                             |
| `locale`             | The locale the write ran under.                                        |
| `changes`            | `{ field: { from, to } }`, or null.                                    |
| `metadata`           | Actor identity, outcome and access mode; correlation ids when present. |
| `title`              | One sentence, such as `Alice updated Posts 'Hello'`.                   |

`resourceLabel` is the first of `_title`, `title`, `name`, `label`, `slug` and
`id` that holds a non-empty string.

`changes` and `metadata` are `f.json()` columns. Values are coerced before they
are stored, so a `Date` arrives as an ISO string and a `bigint` as a string.
The diff leaves out `id`, `createdAt`, `updatedAt` and every key starting with
an underscore.

Fields whose names identify framework credentials are omitted by default. This
includes passwords, passphrases, secrets, tokens, API keys, authorization
values and cookies. You can classify any application field explicitly with
`.audit("include")`, `.audit("redact")` or `.audit("omit")`; an explicit policy
wins over the name-based default. Redacted values are stored as `[REDACTED]`.

Global updates use the same field classification and diff format as collection
updates.

### Who the actor is

| `userName`                           | `userId`            | When                                          |
| ------------------------------------ | ------------------- | --------------------------------------------- |
| The user's name, else email, else id | The session user id | A session is present.                         |
| `System`                             | `system`            | No session, and the call runs in system mode. |
| `Anonymous`                          | null                | No session, and the call runs in user mode.   |

`metadata.actorType` carries the same three cases as `user`, `system` and
`anonymous`. A system context can also pass
`workload: { type, id, name? }`; its id and name replace the generic `system` /
`System` identity so scheduled work and services remain distinguishable.
`requestId`, `traceId`, `actorId`, `actorName` and `outcome: "succeeded"` are
copied into metadata when available.

### The title is rebuilt on read

The stored `title` is English. An `afterRead` hook rewrites it in the reader's
locale when the request carries one. The stored row never changes, so a locale
with no messages falls back to what was written.

## Skipping a resource

```ts title="src/questpie/server/collections/import-runs.ts"
import { collection } from "#questpie/factories";

export const importRuns = collection("importRuns")
	.fields(({ f }) => ({
		name: f.text(120).label("Name").required(),
		payload: f.json().label("Payload"),
	}))
	.admin({ label: "Import runs", audit: false });
```

`audit: false` drops that collection out of the log. Leave the key unset and it
is audited. Globals take the same key on their own `.admin()`. Reach for it on
machine-written tables, heartbeats and caches, the ones that would bury the
entries a person needs to find.

## Reading it back

The log is a private collection by default. System-mode framework work can
query it directly, but user-mode and anonymous reads are denied until your
application grants them explicitly.

```ts
const { docs } = await app.collections.admin_audit_log.find({
	where: { resource: "posts", resourceId: id },
	orderBy: { createdAt: "desc" },
	limit: 20,
});
```

Two REST routes answer the same question for one record.
`GET /:collection/:id/audit` and `GET /globals/:name/audit`, both under your
handler's base path. Each takes `limit`, which defaults to 50, and `offset`.
Each checks the record exists first, and runs under the caller's own access
rules.

To grant read access, redeclare the collection in your own `collections/`
directory and merge the module's builder in. Your file wins, and the merge
keeps the fields, indexes, hooks and admin config. `.access()` replaces the
whole object, so pass every rule, not just `read`.

```ts title="src/questpie/server/collections/audit-log.ts"
import { auditLogCollection } from "@questpie/admin/modules/audit";

import { collection } from "#questpie/factories";

export const auditLog = collection("admin_audit_log")
	.merge(auditLogCollection)
	.access({
		read: ({ session }) => !!session?.user,
		create: false,
		update: false,
		delete: false,
	});
```

The record and global audit routes use this same collection access policy and
its field-level read rules. A rule that hides `changes` therefore hides it from
`GET /:collection/:id/audit` and `GET /globals/:name/audit` too.

## Retention and legal hold

No retention policy means no destructive cleanup. `retention.days: null` also
disables cleanup explicitly. A positive number enables the `audit-cleanup` job,
which runs daily at 03:00 and removes rows older than that many days.

When `legalHold` is present, the job loads expired rows, converts each one to a
`CanonicalAuditEvent`, and preserves every event for which the callback returns
`true`. The callback runs in the application process and may be asynchronous.
It is not a database constraint: direct deletes and a different cleanup process
do not consult it.

## Append-only export

`sink.append(event)` receives the canonical event after the ordinary audit row
is created. The event has a stable `id` and ISO timestamp, a succeeded/failed
outcome, resource and actor identity, optional request/trace ids, changes and
metadata. `toCanonicalAuditEvent()` is exported for consumers that need to
adapt existing flat audit rows to the same shape.

The interface is deliberately small. QUESTPIE does not ship immutable storage,
signing, encryption, ordering guarantees, retries, deduplication, a dead-letter
queue, or a SIEM/WORM vendor integration. Those are responsibilities of the
sink and its deployment. The database collection remains mutable through
system-mode APIs, so it is activity storage, not proof of immutability.

The policy is currently applied by the module's automatic collection/global
hooks and cleanup job. `logAuditEntry()` remains a direct compatibility helper:
it does not invoke the configured sink or delivery policy, and its caller owns
classification of custom `changes` and `metadata`.

<Callout type="warn" title="Compliance primitives are not certification">
	Private reads, field classification, required delivery, retention, legal hold
	and append-only export support security and compliance work. Enabling them
	does not make an application compliant or certified. Access reviews, key
	management, infrastructure controls, retention law, incident response and
	independent assurance remain application and operator responsibilities.
</Callout>

## Upgrading from a public audit collection

The audit collection previously shipped with `read: true`. After upgrading,
ordinary user and anonymous reads return `403` unless you add an explicit
override like the one above. Applications that show audit history in the admin
UI should grant access to the appropriate role before deployment. Do not use
`read: true` unless the complete audit trail is intentionally public.

Credential-like fields are also omitted from new audit diffs by default. If an
unfortunately named non-secret field must remain visible, classify it explicitly
with `.audit("include")`. Existing audit rows are unchanged; migrate or purge
historical values separately if they contain credentials.

To adopt the new policy contract:

1. Run `questpie generate` after adding/upgrading `auditModule`, so the typed
   `config/audit.ts` factory and field `.audit()` extension are current.
2. Grant the narrow read rule your admin UI or API needs before deploying the
   private default.
3. Review credential-like fields and add explicit `include`, `redact` or `omit`
   classifications where names alone are insufficient.
4. Choose `best-effort` or `required`; test database and sink failure behavior
   before selecting required delivery in production.
5. Set retention to `null` or a positive day count, implement legal hold where
   required, and provide your own durable idempotent sink for immutable export.
