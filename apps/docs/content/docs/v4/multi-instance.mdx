---
title: Multiple instances
description: Share PostgreSQL state and route only to compatible Runtime instances.
kind: guide
---

Run compatible Runtime instances against the same PostgreSQL application when
you need more capacity or recovery from a process failure. PostgreSQL owns
Mutation receipts, Change Ledger state, durable runs, and leases.
Application Services remain per-instance resources, not cluster singletons.

Requests, Mutation POSTs, realtime reconnects, and worker claims can reach
different compatible instances. Multiplexed SSE and Fetch/POST need no sticky
routing for correctness. A failed instance loses local connections; another
can reconcile committed state or reclaim eligible expired work.

Compatibility has separate schema, wire, Context/Policy, realtime, executable,
and internal-protocol dimensions. Route a generated client only to servers
supporting its exact digest set. A rejected incompatible request must not be
turned into an automatic Mutation retry against another server.

Retain the builds required by nonterminal durable runs and retained resume state.
Old and new compatible workers claim work only with the required executable
bytes. The [protocol-v9 upgrade](/docs/v4/runtime-and-studio#upgrade-the-internal-protocol)
is explicitly non-rolling; do not mix incompatible protocol versions.

Use the same stable realtime signing key and compatible database connection
configuration across instances. PostgreSQL is the required durable dependency;
optional cache/broker bindings are not shipped setup APIs in beta.2.
Test failure and recovery under your own deployment topology before relying
on a throughput target. Framework correctness is not a capacity guarantee.
