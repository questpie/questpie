Add an optional `schedule` member to an application-owned `defineJob`.
Use a recurring Job to sweep application-owned due rows, such as tickets waiting
for staff follow-up. Keep each sweep bounded; a schedule is not a per-row timer.

## Static schedule

| Member                         | Contract                                               |
| ------------------------------ | ------------------------------------------------------ |
| `schedule.cron`                | Five-field UTC cron expression at minute resolution.   |
| `schedule.execution.principal` | Explicit service Principal, without credentials.       |
| `schedule.execution.context`   | Static input matching the application's Context Codec. |
| `schedule.input`               | Static input matching the Job Codec.                   |

Schedules belong to application Definitions, not Packages. They have no dynamic
CRUD API or named timezones. The selected service Principal still needs current
membership and Policy permission. Keep credentials out of static values.

Place `schedule` directly inside the `defineJob({ ... })` declaration, alongside
`input`, `runAs`, `retry`, and `handler`. The
[deferred rename example](/docs/v4/custom-logic) shows a complete Job and
explicit acceptance; add the schedule member when that same Job needs recurring
static acceptance. Scheduled input and execution Context must be concrete
serializable values, not callbacks or environment reads.

## Activate during deployment

Build, apply the required migrations and Seeds, then run
`questpie schedule activate --expect-revision 0` for the first activation.
Its successful receipt records `acceptedRevision: "1"`. Later deployments
supply the current revision they intend to replace. Keep revisions as decimal
strings, not JavaScript numbers.

`SCHEDULE_ACTIVATION_STALE` means another activation won. Inspect the returned
revision and digest before issuing a new request. If a response is lost, repeat
the exact request against the same built artifacts to recover its receipt.
Runtime startup and migration do not activate schedules.

New or changed programs start strictly after the activation minute. Unchanged
programs retain their frontier. After downtime, the producer accepts only the
latest matching missed minute. Already accepted Jobs retain their own retry
state. PostgreSQL accepts one logical Job/minute tick at most once across workers.

To remove a schedule, remove the member, rebuild, and activate the desired set.
An empty set stops future tick acceptance; it does not cancel accepted runs.
Keep the required [old executable bytes](/docs/v4/durable-reactions#deploy-without-stranding-a-run).

## Named Mutation checkpoints

Inside a Job, call `ctx.run.step.mutation(name, mutationReference, input)`.
The reference is the generated non-callable member, such as
`ctx.mutations.tickets.rename`; the compiler infers the input/result.
Await one step before starting another.

The name, reference, input, and order must remain stable across attempts.
The Mutation commits before fenced checkpoint completion. If the worker crashes
between those commits, the next attempt recovers the same Mutation receipt
without applying the write twice. A checkpoint stores its receipt reference,
not a second result copy.

Fresh Context and Mutation admission still apply to receipt recovery.
Changed/missing history or receipts fail with `CHECKPOINT_INVALID`.
A declared Mutation error rolls back and permanently fails the Job. Cancellation
can race an already dispatched write, so it does not prove rollback.

## Stay within fixed bounds

| Boundary                                           | Limit                                            |
| -------------------------------------------------- | ------------------------------------------------ |
| Scheduled Jobs / artifact                          | 64 / 262,144 canonical bytes                     |
| Calendar years                                     | UTC 1–9999                                       |
| Activation/producer transaction                    | 10 seconds                                       |
| Checkpoint names                                   | 1–64 ASCII letters, digits, hyphen or underscore |
| Ordered checkpoints per run                        | 64, with one command in flight                   |
| Checkpoint reservation/load/completion transaction | 5 seconds                                        |
| Checkpoint input or receipt result                 | 1 MiB                                            |

This seam has no Action checkpoint, Service call, timer, signal, callback step,
or workflow engine. Invalid schedule definitions fail compilation. Artifact or
database-readiness failures require a rebuild or migration before activation;
they do not authorize partial activation. See [deployment](/docs/v4/runtime-and-studio)
for the non-rolling protocol-v9 cutover.
