Run the tutorial against your own disposable PostgreSQL database. Complete the
[data](/docs/v4/data-and-queries) and [Mutation](/docs/v4/queries-and-mutations)
chapters first. This guide uses a trusted server script so you can test the data
flow before connecting an Auth provider or browser.

## Prepare PostgreSQL

Use PostgreSQL 16 or newer, UTF-8 encoding, `C.UTF-8` database locale, and the
built-in deterministic `C` collation, matching `questpie.json`. Create a fresh
database whose application schema `barbershop_support` does not yet exist.
Set `DATABASE_URL` in your shell to that database's connection string.
Use a direct/session-affine connection for migration and Runtime work.

Set `QUESTPIE_REALTIME_HMAC_KEY` to a secret of at least 32 bytes encoded as hex.
Keep the same key across compatible Runtime instances and restarts. These are
server environment values; do not commit them or place them in browser code.

If you use Docker for local development, this creates a separate PostgreSQL 17
container with the required locale. It requires Docker and OpenSSL. Keep the
generated password in your local environment for later terminals.

```sh
export BARBERSHOP_DB_PASSWORD=$(openssl rand -hex 16)
docker run --name barbershop-postgres --detach \
  --publish 127.0.0.1:54329:5432 \
  --env POSTGRES_PASSWORD="$BARBERSHOP_DB_PASSWORD" \
  --env POSTGRES_DB=barbershop \
  --env 'POSTGRES_INITDB_ARGS=--encoding=UTF8 --locale=C.UTF-8' \
  postgres:17
export DATABASE_URL="postgresql://postgres:$BARBERSHOP_DB_PASSWORD@127.0.0.1:54329/barbershop"
export QUESTPIE_REALTIME_HMAC_KEY=$(openssl rand -hex 32)
docker exec barbershop-postgres pg_isready -h 127.0.0.1 -U postgres -d barbershop
```

Wait until `pg_isready` reports “accepting connections” before planning.
An existing container or occupied port is not replaced; choose another name/port
and update the connection string in that case. To pause this local database,
run `docker stop barbershop-postgres`; resume it with `docker start barbershop-postgres`.
The container retains its data until you remove it.

## Plan, review, and create the migration

Run in the application directory:

```sh
bunx --no-install questpie migration plan --name create-support
```

The JSON result contains `path`, `digest`, `classification`, and the full `plan`.
Review the schema, fields, constraints, and relations in that plan. `safe`
adds state; `guarded` may lock or fail on existing data; `destructive` can remove
or narrow state; `blocked` cannot be committed by this migration protocol.

Copy the exact returned path into `PLAN_FILE`, then create the artifact:

```sh
PLAN_FILE='.questpie/plans/<digest-from-plan-result>.json'
bunx --no-install questpie migration create --plan "$PLAN_FILE"
```

This writes six files under `questpie/migrations/000001_create-support/`.
Review and commit all six, including `up.sql` and `checksum.sha256`.
Do not edit the generated SQL. Creation does not apply database changes.

When `DATABASE_URL` is set, planning checks the live database against the local
base. Without it, planning is offline and application checks happen at apply.
The same source and history produce the same Plan bytes in both modes.

## Add deterministic demo data

Create this source Seed. Its fixed IDs let the next script select the same
Barbershop ticket on every run. This is demo data, not a user or session Seed.

Seed timestamps use canonical ISO strings in the committed JSON artifact.
Operation results decode those timestamps to JavaScript `Date` objects.

```ts title="src/data/demo-seed.ts"
import { defineSeed, seed } from "questpie";
import { tickets } from "./tickets";
import { comments } from "./comments";

export const supportDemo = defineSeed({
	name: "barbershopSupport.demo.v1",
	steps: [
		seed.insert(tickets, {
			id: "018f5f6e-5f2c-7b41-a854-3d9a6b6b7131",
			summary: "Can I move my appointment?",
		}),
		seed.insert(comments, {
			id: "018f5f6e-5f2c-7b41-a854-3d9a6b6b7132",
			ticketId: "018f5f6e-5f2c-7b41-a854-3d9a6b6b7131",
			body: "I can come on Friday instead.",
			createdAt: "2026-09-09T09:00:00.000Z",
		}),
	],
});
```

Persist new Seed artifacts, rebuild the bundle with the committed migration,
then apply the migration and Seed:

```sh
bunx --no-install questpie seed create
bunx --no-install questpie build
bunx --no-install questpie migration apply
bunx --no-install questpie seed apply
```

`seed create` writes three immutable files per new Seed under `questpie/seeds/`.
Commit them. Repeating apply recovers the existing receipts and does not insert
the rows twice. To change initialized data later, author a new Seed identity;
do not edit the old one. `dependsOn` orders dependent Seeds.

## Execute the typed read and write

Create this script outside `src/`. It supplies a trusted user Principal because
you run it on the server. It is not an authentication endpoint and accepts no
browser-supplied Principal. The tutorial Policy allows any authenticated user
and does not isolate shops by tenant.

```ts title="scripts/try-ticket.ts"
import { createApp } from "#questpie/app";
import { principal } from "questpie";

const connectionUrl = process.env.DATABASE_URL;
const encodedKey = process.env.QUESTPIE_REALTIME_HMAC_KEY;
if (
	!connectionUrl ||
	!encodedKey ||
	!/^(?:[0-9a-fA-F]{2}){32,}$/.test(encodedKey)
)
	throw new Error("Set DATABASE_URL and a hex QUESTPIE_REALTIME_HMAC_KEY");

const app = await createApp({
	postgres: { connectionUrl, directConnectionUrl: connectionUrl },
	realtime: { hmacKey: Uint8Array.from(Buffer.from(encodedKey, "hex")) },
	maintenance: { authorize: () => false },
});
try {
	const result = await app.execution(
		{
			principal: principal.user({ id: "018f5f6e-5f2c-7b41-a854-3d9a6b6b7133" }),
			context: { tenantId: "018f5f6e-5f2c-7b41-a854-3d9a6b6b7134" },
			signal: AbortSignal.timeout(5_000),
		},
		async ({ queries, mutations }) => {
			const id = "018f5f6e-5f2c-7b41-a854-3d9a6b6b7131";
			await mutations.tickets.rename(
				{ id, summary: "Please move my appointment" },
				{ callId: "barbershop-demo-rename-v1" },
			);
			return queries.tickets.detailPage({ ids: [id], first: 1, after: null });
		},
	);
	console.log(result.nodes[0]?.summary);
} finally {
	await app.close();
}
```

Run `bun scripts/try-ticket.ts`. It prints `Please move my appointment`.
Run it again: the same Mutation identity and input recover the committed receipt.
The Query reads the updated row. The script always closes its Runtime.

To serve network requests instead, run `bunx --no-install questpie start`. Configure
[Auth](/docs/v4/auth) before using the protected ticket from a browser;
the direct script's Principal is not a browser session.

## Change the schema safely

Edit source, make a new named plan, review it, and create the next artifact.
Explicit renames use repeated `--rename fromIdentity=toIdentity` arguments.
The planner never guesses a rename. Destructive creation also requires
`--accept-destructive` with the exact returned digest. A generic force flag
cannot substitute for it.

`QP-SCHEMA-020` requires that acknowledgment. `QP-SCHEMA-022` means source or
history changed since planning: make a fresh plan. `QP-SCHEMA-023` means stored
artifact bytes do not match their checksum. Recover the original reviewed
artifact; do not recalculate a checksum around edited SQL.

A failed apply can leave earlier migrations committed because each migration
owns its own transaction. Keep the application stopped, inspect the failure,
and repair forward. Rebuild after adding committed artifacts, then follow
[deployment](/docs/v4/runtime-and-studio).
