Import `defineJob` and `defineReaction` from `#questpie/app`, and `durable`,
`codec`, and `operation` from `questpie`. Use
[custom logic](/docs/v4/custom-logic) to decide whether work needs durability.

## Definitions and acceptance

Both kinds declare a stable name, input/output contract, run-as rule, bounded
retry policy, and a handler. `durable.caller({ whenDenied: "fail" })` records
the caller relationship; attempts resolve fresh Context and authorization.

A Job is accepted explicitly through its generated server capability, with
optional `notBefore` for an absolute due time. A Mutation can accept it in the
same transaction as a business write. Reaction dispatch instead represents an
explicit committed fact. Rollback preserves neither the write nor its dispatch.
Neither kind is a generic browser Job-control API.

## Attempts and retries

`durable.retry` specifies `maximumAttempts`, `initialDelay`, `backoff`,
`maximumDelay`, `jitter`, and `horizon`. Retries, attempts, leases, cancellation,
and retained run identity live in PostgreSQL. Worker ownership is fenced;
a stale attempt cannot claim successful completion after losing its lease.
A provider request can still be uncertain after the worker loses contact.

The ordinary CLI starts worker polling. A custom host must create a worker,
poll it, and own drain/cleanup. A Fetch mount alone does not run Jobs.

## External effects

A Reaction can declare literal effect names and use its generated
`ctx.run.effect(name).invoke({ input, perform, recover })` handle. The provider
receives stable effect identity for idempotency/reconciliation. A changed input
cannot reuse a recorded effect identity silently.

Durable acceptance does not make an email provider transactional. Persisted
intent, a performed external effect, and confirmed delivery are different facts.
Use provider recovery rather than declaring an uncertain effect unsuccessful
and sending it again blindly.

## Deploy without stranding a run

Nonterminal runs can require their original Runtime Build and executable bytes.
Retain compatible workers/artifacts until that work finishes. Removing a source
Definition or replacing a build does not migrate retained work automatically.
Maintenance operations require explicit host authorization and exact identities;
there is no default browser/admin bypass.

For recurring work and recoverable transactional steps, see
[schedules and checkpoints](/docs/v4/scheduled-jobs). A Job checkpoint is a named
Mutation call, not an arbitrary external-effect callback.
