QUESTPIE uses one durable run engine for three different application jobs:

- a Job is explicitly requested background work;
- a Reaction follows one exact committed application fact; and
- a Workflow is the same Durable Run with checkpointed Mutation, Action,
  timer, signal, and history capabilities.

They share acceptance, attempts, leases, retry, cancellation, results,
retention, executable compatibility, and operational events. They do not share
one universal builder that exposes every capability everywhere.

## Define explicit background work

```ts title="src/features/company-digest.ts"
import { defineJob } from "#questpie/app";
import { codec, durable } from "questpie";

export const companyDigest = defineJob({
	name: "reports.companyDigest",
	input: codec.object({ companyId: codec.uuid() }),
	runAs: durable.caller({ whenDenied: "fail" }),
	retry: durable.retry({
		maximumAttempts: 5,
		initialDelay: "1s",
		backoff: "exponential",
	}),
	async handler({ input, ctx, attempt }) {
		await attempt.heartbeat({ completed: 1 });
		return { companyId: input.companyId, actorId: ctx.principal.id };
	},
});
```

Server code dispatches a Job from the generated application projection. The
idempotency key names one logical request; a delay changes when it becomes
claimable, not its identity:

```ts
const accepted = await app.execution(executionInput, ({ jobs }) =>
	jobs["reports.companyDigest"].dispatch(
		{ companyId },
		{ idempotencyKey: `digest:${companyId}:${date}`, delay: "10m" },
	),
);
```

A client does not receive generic Job controls. Author a normal
Policy-protected Mutation when browser callers should request work, and return
only the receipt your application wants to disclose.

A recurring schedule accepts independently deduplicated Job runs. Removing the
schedule prevents future ticks; it never cancels work already accepted.

## Keep Reaction causation exact

A Reaction has no independent producer and no author-supplied second dedup key.
Its identity derives from the application, Reaction Resource, committed
transaction and fact, and static dispatch slot. Rollback produces neither the
fact nor the run. Review [Run a durable Reaction after commit](./durable-reactions)
for the complete transaction-owned path.

## Checkpoint a Workflow without arbitrary callbacks

A Workflow adds a closed `step` projection:

```ts
await step.mutation("request-review", mutations.articles.requestReview, {
	articleId: input.articleId,
});

const approval = await step.waitForSignal("wait-for-approval", {
	signal: "approval",
	timeout: "30d",
});

const publication = await step.action(
	"publish",
	actions.publishing.publishExternally,
	{ articleId: input.articleId, approvedBy: approval.approvedBy },
);
```

`step.mutation` persists one stable Mutation Call Identity and validated result.
`step.action` persists one stable Effect Identity and receipt or explicit
ambiguity. `step.sleep` writes a durable timer. `step.waitForSignal` consumes a
typed, authorized, deduplicated durable signal.

There is no `step.run(async () => arbitraryEffect)`. Code outside a checkpoint
may run again after a crash, so it cannot own an application write, provider
effect, clock, or random value.

Step names are unique and ordered. Each command has canonical bytes that must
match history. A live run pins its Workflow semantic version and executable
digest; a deployment cannot replay it against arbitrary latest code.

The complete Workflow product is deliberately deferred. Signal authorization,
child work, compensation, continuation and history limits, and multi-version
evolution must pass their focused vertical before Workflow becomes a supported
public release surface. The shared kernel and compatibility seam are fixed now
so that later breadth does not require a second runtime.

## Map lifecycle work to its owner

QUESTPIE does not expose a general `before*` or `after*` hook catalogue:

| V3 job           | Use in v4                                                                                                      |
| ---------------- | -------------------------------------------------------------------------------------------------------------- |
| `beforeValidate` | runtime codecs and closed pure normalization/validation; a named Mutation for application-dependent validation |
| `beforeChange`   | closed server values or a named Mutation inside its transaction                                                |
| `afterChange`    | transaction-joined audit/write plus exact committed durable dispatch                                           |
| `afterRead`      | selection/output codec, closed pure projection, or a named Query in its read snapshot                          |

This keeps pure input work, transaction-owned work, selected-output work, and
post-commit durable work separate. A Reaction is not a generic lifecycle hook.

## Understand the guarantees

PostgreSQL owns every run, attempt, lease, schedule, timer, signal, history,
result, and retention transition. Notifications or brokers may reduce latency;
losing them cannot lose accepted work.

Every attempt constructs a fresh ordinary Execution, resolves Context once,
checks current Policy, and cleans up its Services. Physical execution is at
least once. Fencing rejects a stale worker. Cancellation is cooperative and
cannot recall a provider effect already accepted.

Studio consumes the same append-only Execution Envelope events as the Runtime.
It can correlate acceptance, attempts, leases, retries, cancellation,
checkpoints, signals, ambiguity, and terminal state without exposing payloads,
credentials, Context, Service state, or database URLs.

QUESTPIE authors only B-tree Indexes for this state and emits no RLS claim.
