Define the tickets and comments that Barbershop staff will read. A ticket has
an ID and a summary. Each comment belongs to one ticket. The Query returns one
ticket and at most 50 visible comments.

Complete [installation](/docs/v4/installation) first. Create each file below.

## Store rows and declare the relation

The comment owns the foreign key. The ticket declares the inverse relation so
its Query can select comments. The primary key is explicit; an `id` field alone
does not establish one.

```ts title="src/data/tickets.ts"
import {
	constraint,
	defineCollection,
	field,
	relation,
	relationRef,
} from "questpie";

export const tickets = defineCollection({
	name: "tickets",
	fields: {
		id: field.uuid({ nullable: false }),
		summary: field.text({ nullable: false, minLength: 1, maxLength: 500 }),
	},
	constraints: {
		primary: constraint.primaryKey({ fields: ["id"] }),
	},
	relations: {
		comments: relation.toMany({
			inverseOf: relationRef("comments", "ticket"),
		}),
	},
});
```

```ts title="src/data/comments.ts"
import { constraint, defineCollection, field, relation } from "questpie";
import { tickets } from "./tickets";

export const comments = defineCollection({
	name: "comments",
	fields: {
		id: field.uuid({ nullable: false }),
		ticketId: field.uuid({ nullable: false }),
		body: field.text({ nullable: false, minLength: 1, maxLength: 8_192 }),
		createdAt: field.timestamp({ nullable: false, withTimezone: true }),
	},
	constraints: {
		primary: constraint.primaryKey({ fields: ["id"] }),
	},
	relations: {
		ticket: relation.toOne({
			target: tickets,
			fields: ["ticketId"],
			references: ["id"],
		}),
	},
});
```

## Resolve Context and allow reads

This tutorial teaches a single shared staff inbox. Its Policy admits every
authenticated Principal. It does **not** implement tenant isolation: `tenantId`
is Context input, but these Collections have no tenant field or membership rule.
Use [Auth and permissions](/docs/v4/auth) before adapting it for private shops.

```ts title="src/context.ts"
import { codec, context, defineContext } from "questpie";

export const appContext = defineContext({
	name: "app.context",
	input: codec.object({ tenantId: codec.uuid() }),
	resolve: ({ input }) => ({
		tenant: context.tenant({ id: input.tenantId }),
		values: {},
	}),
});
```

```ts title="src/data/policies.ts"
import { definePolicy, expr, policy } from "questpie";
import { comments } from "./comments";
import { tickets } from "./tickets";

export const ticketPolicy = definePolicy(tickets, {
	name: "tickets.default",
	read: {
		admit: policy.authenticated(),
		rows: () => expr.always(),
	},
});

export const commentPolicy = definePolicy(comments, {
	name: "comments.default",
	read: {
		admit: policy.authenticated(),
		rows: () => expr.always(),
	},
});
```

## Select one ticket with its comments

The root page is bounded to one ticket. Both orders end in a unique key, so
pagination has a stable order. The child list has a fixed bound and no cursor.
The example excludes comments whose body is exactly `filtered` to show where
an application filter belongs.

```ts title="src/queries/ticket-detail.ts"
import { codec } from "questpie";
import { defineQuery } from "#questpie/app";
import { comments } from "../data/comments";
import { tickets } from "../data/tickets";

export const ticketDetailPage = defineQuery({
	name: "tickets.detailPage",
	network: true,
	query: tickets.list({
		parameters: {
			ids: codec.list(codec.uuid(), { maximum: 1 }),
			first: codec.integer({ minimum: 1, maximum: 1 }),
			after: codec.nullable(codec.cursor()),
		},
		where: ({ row, parameters }) => row.id.in(parameters.ids),
		orderBy: { id: "asc" },
		select: {
			id: true,
			summary: true,
			comments: comments.list({
				first: 50,
				where: ({ row }) => row.body.notEqual("filtered"),
				orderBy: { createdAt: "desc", id: "desc" },
				select: { id: true, body: true, createdAt: true },
			}),
		},
		page: ({ parameters }) => ({
			first: parameters.first,
			after: parameters.after,
		}),
	}),
});
```

## Build and inspect the result

Run `bun run build`, then `bun run types:check`. The generated client now has
`queries["tickets.detailPage"]`. You did not write a response interface or an
endpoint handler.

At runtime, a successful call returns `nodes` and `pageInfo`. `nodes` contains
zero or one ticket. Each ticket has `id`, `summary`, and a readonly `comments`
array. Each comment has `id`, `body`, and `createdAt`, decoded as a `Date`.
No visible ticket produces an empty `nodes` array. No visible comments produces
`comments: []`. A missing or invisible row has the same result.

[Call this Query](/docs/v4/clients) once your matching database and Auth host
are ready. Compilation alone does not insert a ticket or provision the database.
See [schema lifecycle](/docs/v4/schema-lifecycle) for the current setup limit.
