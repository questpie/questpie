Deploy the same built application whose migrations you reviewed. The Runtime
owns network requests, realtime, and worker polling in one long-lived process.
For a fresh local database follow [the Barbershop setup](/docs/v4/schema-lifecycle).

## Build, migrate, and start

Configure `DATABASE_URL` and a stable `QUESTPIE_REALTIME_HMAC_KEY` containing at
least 32 bytes as hex. The CLI uses the database URL for both ordinary and direct
connections. Select a compatible direct/session-affine connection.

```sh
bunx --no-install questpie build
bunx --no-install questpie migration apply
bunx --no-install questpie seed apply
bunx --no-install questpie start --port 3000
```

Run Seed apply when the application has committed Seeds. Startup never creates
or applies a migration. It verifies the application, schema, migration head,
Runtime Build, executable bindings, and internal protocol before accepting work.
Rebuild after committing new migration/Seed artifacts.

The ticket tutorial requires authenticated access. Configure its
[credential resolver](/docs/v4/auth) before using it from a browser; without an
Auth integration requests have no verified user identity.

## Health and cleanup

The Runtime does not provide built-in liveness or readiness HTTP endpoints.
Unmatched paths return 404. A custom host must expose its own probes and use
its startup/shutdown state to decide when to accept traffic.

For a custom host, create the generated App, own its Fetch listener and worker
polling, and always close it. See [escape hatches](/docs/v4/escape-hatches).
There are no split API/worker roles or a shipped Studio/admin UI.

## Upgrade the internal protocol

Beta.2 requires exact internal protocol v9. Stop incompatible Runtime
instances before applying the upgrade. This is a non-rolling cutover.

| Existing database | Required `migration apply` flags                                             |
| ----------------- | ---------------------------------------------------------------------------- |
| Fresh             | None                                                                         |
| v8                | `--allow-non-rolling-protocol-v9`                                            |
| Supported v6/v7   | Both `--allow-non-rolling-protocol-v8` and `--allow-non-rolling-protocol-v9` |

Each upgrade commits separately. A failed v9 step can leave a valid committed
v8 database; keep incompatible processes stopped and repair forward.
There is no in-place downgrade. Retain executable bytes needed by nonterminal
Jobs/Reactions until those runs finish.

Migrations and startup do not activate schedules. After migration and Seeds,
use [explicit schedule activation](/docs/v4/scheduled-jobs).

## Operational limits

The default startup and drain deadlines are 30 seconds. Request and response
bodies are bounded to 1 MiB, and active root executions per Principal to 64.
`RESOURCE_LIMIT` and `RUNTIME_UNAVAILABLE` are explicit failures; an uncertain
write still needs its own recovery identity.

For multiple instances use [the deployment constraints](/docs/v4/multi-instance).
For execution diagnostics configure [OpenTelemetry](/docs/v4/opentelemetry).
Backups, database retention, and provider operations remain your responsibility.
