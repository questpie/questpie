Import `defineQuery`, `defineMutation`, `defineAction`, `defineRoute`,
`defineJob`, and `defineReaction` from `#questpie/app`. Build first to generate
the current application types. Use [custom logic](/docs/v4/custom-logic) to
choose a kind, or follow the [Mutation tutorial](/docs/v4/queries-and-mutations).

## Query, Mutation, and Action

All three kinds require a stable `name`. Set `network: true` to expose a
network Operation. Optional `describe` carries a summary, description, and examples.

| Kind     | Required handler definition members                                                                                                                                 |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Query    | `input`, `output`, `handler({ input, ctx })`. No authored `policy` or `errors` member; Collection Policy governs reads.                                             |
| Mutation | `input`, `output`, `policy`, `errors`, `handler({ input, ctx, errors })`. Use `errors: {}` when there are no declared errors.                                       |
| Action   | `input`, `output`, `policy`, `errors`, `limits`, `handler({ input, ctx, effect, errors })`. Limits require `inputBytes`, `resultBytes`, and `durationMilliseconds`. |

Declare an error with `operation.error({ code, status, payload? })`.
The compiler can infer supported closed outputs; pin recursive outputs explicitly.

A plan-backed Query uses `query: collection.list(...)` instead of a handler.
Its parameters and selected result derive the input/output contract.
Do not provide two independent implementations of the read.

| Kind     | Generated capabilities and boundary                                                                       |
| -------- | --------------------------------------------------------------------------------------------------------- |
| Query    | Policy-aware reads in one snapshot; no writes, dispatch, raw SQL, or external effects.                    |
| Mutation | Policy-aware reads and writes in one PostgreSQL transaction, stable `ctx.now`, atomic durable acceptance. |
| Action   | Explicit external invocation using declared effects; no shared transaction with the provider.             |
| Route    | Standard Request/Response handling with explicit path, method, credentials, admission and limits.         |
| Job      | Durable work accepted explicitly, delayed, or by a static schedule.                                       |
| Reaction | Durable work caused by a transactionally dispatched committed fact.                                       |

## Collection writes

The default Collection Policy’s declared `create` and `update` rules generate
those data capabilities for named Mutations. `get`, `delete`, and `list` need
their corresponding authored Collection Operation Set members.

A named Mutation calls `ctx.data.collectionName.create`, `get`, `update`, or
`delete` with generated types. Keyed updates take `key` and caller `patch`;
trusted assignments use the separate `values` member. The complete candidate
still passes validation, Policy, and PostgreSQL constraints.

Collection Operation Sets from `defineCollectionOperations` expand selected
CRUD members into ordinary Queries/Mutations at compile time. They create no
second runtime or automatic network access. Use explicit named Operations when
the command has business meaning, such as `tickets.rename`.

## Collection Operation Sets

`defineCollectionOperations(collection, body)` comes from `questpie`.
The body requires `name` and a Policy bound to that Collection. Optional
`network: true` publishes its selected members; omission keeps them internal.
Named Mutations already have generated data access.
The Barbershop `tickets.rename` does not need a CRUD Operation Set.

| Member             | Required shape                                                         |
| ------------------ | ---------------------------------------------------------------------- |
| `list`             | `{ data }`, where `data` is a structural data Query.                   |
| `get`, `delete`    | `{ select }`, a Field selection map.                                   |
| `create`, `update` | `{ input, select }`; `input` is a literal array of caller Field names. |

Each member supports `describe`. Writes also support `normalize`, `values`,
`errors`, and `issueMappings`. The `values` callback receives symbolic `input`,
`principal`, `tenant`, and `operationTime`. These are compiled Value Program
operands, not arbitrary runtime values. `mutation.overwrite(operand)` marks an
explicit trusted overwrite inside that callback; it does not bypass Policy or
make an immutable or database-owned Field writable.

## Collection lifecycle

| Phase        | What belongs here                                                              |
| ------------ | ------------------------------------------------------------------------------ |
| `normalize`  | Pure input normalization.                                                      |
| `validate`   | Pure candidate invariants.                                                     |
| `check`      | Bounded Policy-aware transactional reads to check an invariant.                |
| `afterWrite` | Bounded sequential transactional work before commit, including Job acceptance. |

These functions compile to a restricted Lifecycle Program. They do not execute
as arbitrary JavaScript callbacks. They cannot call a mail provider, read a
Request, open a raw transaction, start timers, or launch detached work.

`collection.issue()` creates a payloadless internal invariant identity.
`validate` and `check` can raise it. Each named Mutation must map all reachable
issues with `issueMappings` to its own declared payloadless errors. Unmapped or
forged issues roll back and become `INTERNAL`. A Collection issue is not an
HTTP error definition.

## Results, errors, and recovery

The Runtime validates input and output codecs. A declared error is created with
`errors.member(...)`; React adapter bindings narrow it with their
`isError` guard. It is distinct from a transport or framework failure.

A Mutation receipt binds application, Tenant, Operation, Principal, `callId`,
and canonical input. Exact replay recovers the stored result; changed input
raises `IDEMPOTENCY_CONFLICT`. `COMMITTED_RESULT_UNAVAILABLE` means the write
committed but the response could not be produced. Recover using the same identity;
a cancelled or lost response does not prove rollback.

An Action requires caller `effectKey` material for its declared effects.
`ACTION_OUTCOME_AMBIGUOUS` after dispatch is not permission to retry blindly. Use the
provider's idempotency or reconciliation support.

## Routes

`defineRoute` declares `name`, `method`, `path`, `policy`, `credentials`,
`limits`, and a handler returning a standard Response. `credentials: "none"`
is useful for the Auth provider's own public sign-in route; it does not grant
access to protected data. Routes are outside the generated JSON Operation
client, OpenAPI Operation projection, and MCP tools.
