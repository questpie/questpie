---
title: Hooks
description: Run your code at each stage of a collection's create, update, read, delete, and purge lifecycle, to transform input, derive fields, enforce rules, and fire side effects only after the write commits.
---

Hooks run logic at precise points in a collection lifecycle: transform input before validation, compute fields before a write, react to the saved record, and schedule side effects after commit. One `.hooks({ ... })` declaration governs REST, typed client, admin, and internal operations.

## What it does

- **Transform input before validation**, normalize, trim, and default values in `beforeValidate` by mutating `ctx.data` in place.
- **Derive fields and run business logic** on validated input in `beforeChange`, slugs, computed columns, cross-field checks, the last chance to change what gets written.
- **Revalidate related durable facts** in `beforeWrite`, after the mutation rows are claimed but before any write or transaction-bound effect.
- **React to a completed write** in `afterChange` with the full saved record, plus `ctx.original` on update so you can diff old versus new.
- **Shape query output** in `afterRead`, add computed fields, format values, redact.
- **Guard and clean up deletes** with `beforeDelete` (block, cascade, back up) and `afterDelete` (cleanup, notify).
- **Guard irreversible purge** with dedicated, fatal `beforePurge` and `afterPurge` hooks.
- **Fire side effects only after the transaction commits** with `ctx.onAfterCommit`, jobs, emails, webhooks, search indexing.
- **Abort an operation** by throwing in a transaction-bound hook.

## Quick start

Add a `.hooks({ ... })` block to any collection. This one generates a slug before the write, then dispatches a notification job, but only once the row is committed:

```ts title="src/questpie/server/collections/posts.ts"
import { collection } from "#questpie/factories";

function slugify(input: string): string {
	return input
		.toLowerCase()
		.replace(/[^a-z0-9]+/g, "-")
		.replace(/^-|-$/g, "");
}

export const posts = collection("posts")
	.fields(({ f }) => ({
		title: f.text(255).required(),
		slug: f.text(255),
		body: f.richText(),
	}))
	.hooks({
		// Runs after validation, before the INSERT/UPDATE. Mutate `data` in place.
		beforeChange: ({ data, operation }) => {
			if (operation === "create" && data.title && !data.slug) {
				data.slug = slugify(data.title);
			}
		},

		// Runs after the write, INSIDE the CRUD transaction.
		// Queue publish joins that transaction automatically.
		afterChange: async ({ data, operation, queue }) => {
			if (operation !== "create") return;
			await queue.notifyPost.publish(
				{ postId: data.id },
				{ idempotencyKey: `post-notify:${data.id}` },
			);
		},
	});
```

That's the whole surface for most collections: one or two `before*` hooks to shape data, one `afterChange` to react. Every stage and every `ctx` property is in [Full API](#full-api) below.

<Callout type="info">
	**Hooks merge across calls.** Each call to `.hooks()` *appends* to the
	existing handlers per stage, it never replaces them. Calling `.hooks()` twice,
	or composing a collection from modules, accumulates handlers for each stage
	and runs them in registration order. (Contrast with `.access()`, which
	overwrites the whole access object on each call.)
</Callout>

## Example: what each hook receives

On an update, `afterChange` receives both the saved record (`ctx.data`) and the pre-update record (`ctx.original`), so you can diff and act only on a real change:

```ts title="src/questpie/server/collections/posts.ts"
.hooks({
	afterChange: ({ data, original, operation, onAfterCommit, email }) => {
		if (operation === "update" && original && data.status !== original.status) {
			onAfterCommit(async () => {
				await email.sendTemplate({
					template: "postStatusChanged",
					input: { title: data.title, status: data.status },
					to: data.authorEmail,
				});
			});
		}
	},
})
```

Written **inline** on `.hooks({ ... })`, `data` / `original` / `operation` are already narrowed to the `posts` row with no annotations:

```ts
// data:      CollectionDoc<"posts">              (the saved record)
// original:  CollectionDoc<"posts"> | undefined   (set only on update)
// operation: "create" | "update"
```

<Callout type="warn">
	**`ctx.original` holds the previous record only on update.** It is exposed at
	all only on `afterChange` and `afterRead`, and is populated (non-`undefined`)
	*only* for the `update` operation. On those two hooks its type is
	`CollectionDoc<K> | undefined` on **every** branch (including create / delete /
	read), so it's not `never`-typed there, it's simply `undefined` at runtime on
	the non-update operations. Always branch on `ctx.operation === "update"` before
	reading it.

    `afterDelete` exposes the deleted row as both `data` and `original`.
    `beforePurge` and `afterPurge` expose the same locked, localized persisted
    preimage as both values. Purge deliberately skips field-output and
    `afterRead` hooks, so derived output such as an upload URL is not present.
    On the remaining hook stages, `original` is `never`-typed.

</Callout>

## Full API

### Lifecycle stages

Declare any subset of these on `.hooks({ ... })`. Each value is a **single function or an array of functions**, see [Arrays and composition](#arrays-and-composition).

| Stage              | Fires on                            | `ctx.data`                 | `ctx.original`         | Throw aborts?                     |
| ------------------ | ----------------------------------- | -------------------------- | ---------------------- | --------------------------------- |
| `beforeOperation`  | create, update, read, delete, purge | input (type depends on op) | none                   | yes                               |
| `beforeValidate`   | create, update                      | **mutable** input          | none                   | yes                               |
| `beforeChange`     | create, update                      | **validated** input        | none                   | yes                               |
| `beforeWrite`      | create, update, delete, restore     | readonly validated input   | fresh locked record(s) | **yes**, propagates + rolls back  |
| `afterChange`      | create, update                      | the saved record           | record (update only)   | **yes**, propagates + rolls back  |
| `beforeRead`       | read                                | query options              | none                   | yes                               |
| `afterRead`        | create, update, read, delete        | the record                 | record (update only)   | **yes**, propagates to the caller |
| `beforeDelete`     | delete                              | record to be deleted       | none                   | yes                               |
| `afterDelete`      | delete                              | the deleted record         | same deleted record    | **yes**, propagates + rolls back  |
| `beforePurge`      | purge                               | locked deleted preimage    | same preimage          | **yes**, propagates + rolls back  |
| `afterPurge`       | purge                               | locked deleted preimage    | same preimage          | **yes**, propagates + rolls back  |
| `beforeTransition` | workflow transition                 | the record                 | none                   | yes                               |
| `afterTransition`  | workflow transition                 | the record                 | none                   | no, caught + logged               |

`beforeTransition` / `afterTransition` fire only on workflow stage transitions and carry a different context, see [Transition hooks](#transition-hooks). See [Aborting an operation](#aborting-an-operation) for the transaction boundary of each stage.

**Execution order**, per operation:

```
Create  →  beforeOperation → beforeValidate → beforeChange → [claim] → beforeWrite → [INSERT] → afterChange → afterRead
Update  →  beforeOperation → beforeValidate → beforeChange → [claim] → beforeWrite → [UPDATE] → afterChange → afterRead
Delete  →  beforeOperation → beforeDelete   → [claim] → beforeWrite → [DELETE] → afterDelete → afterRead
Purge   →  beforeOperation → beforePurge    → [PURGE]  → afterPurge
Read    →  beforeOperation → beforeRead     → [SELECT] → afterRead
```

`afterRead` is the output hook for create, update, delete, and read; purge returns only `{ success: true }` and does not expose the removed record through `afterRead`. Branch on `ctx.operation` to discriminate inside it. (The upload feature auto-injects an `afterRead` hook to generate file URLs, an `afterDelete` hook for committed hard deletes, and an `afterPurge` hook that transactionally records durable provider cleanup; your hooks run alongside these.)

<Callout type="info" title="Create and update share change hooks">
	Use `beforeValidate`, `beforeChange`, and `afterChange` for both operations,
	then branch on `ctx.operation === "create"` when behavior differs. Globals use
	`beforeUpdate` and `afterUpdate`. See [Globals](#related).
</Callout>

### Transaction-bound hooks

`beforeWrite`, `afterChange`, `afterDelete`, and `afterPurge` run inside the owning CRUD
transaction. Their `ctx.db` is that active transaction, and injected services
such as `collections`, `queue`, and `channels` join the same scope. A thrown or
rejected error fails the CRUD call and rolls back the row plus all
transaction-joined work:

```ts title="src/questpie/server/collections/posts.ts"
export const posts = collection("posts")
	.fields(({ f }) => ({
		title: f.text().required(),
	}))
	.hooks({
		afterChange: async ({ data, operation, channels }) => {
			await channels.publish("postActivity", {
				params: { postId: data.id },
				event: operation === "create" ? "created" : "updated",
				data: { id: data.id },
			});
		},
	});
```

Exact coverage:

- `afterChange`: once per successful create or update winner. `restoreById`
  and version reverts use the update lifecycle; an already-active no-op restore
  does not run an effect.
- `afterDelete`: once per successful soft or hard delete winner.
- `afterPurge`: after physical removal and before commit.
- `updateMany` and `deleteMany`: once per winning row, with the normal bulk
  metadata.
- `updateBatch`: once per successful item, without bulk metadata. Each item
  invokes the ordinary single-record update lifecycle inside the shared
  transaction.

A nested managed transaction does not run a hook a second time. Bulk hook
chains execute sequentially in deterministic winner order so one rejection is
fully settled before the transaction rolls back.

`afterRead` still runs after the transaction closes. Do not perform direct
email, HTTP, or other work that cannot join the database transaction in an
`after*` hook; use `onAfterCommit` or a transaction-aware queue/outbox instead.

### Transactional dependent-row fact guards

Use `beforeWrite` when a generated mutation depends on current facts in another
collection. It runs after the mutation's primary rows have been claimed and freshly read,
inside the exact write transaction, but before relation persistence, cascade,
version, primary-row DML, or transaction-bound effects:

```ts title="src/questpie/server/collections/memberships.ts"
collection("memberships")
	.fields(({ f }) => ({
		account: f.relation("accounts").required(),
		label: f.text().required(),
	}))
	.hooks({
		beforeWrite: {
			locks: ({ method, data }) =>
				method !== "updateBatch" && "account" in data && data.account
					? [{ collection: "accounts", ids: [data.account] }]
					: [],
			run: async (ctx) => {
				if (
					ctx.method === "updateBatch" ||
					!("account" in ctx.data) ||
					!ctx.data.account
				)
					return;
				const account = await ctx.collections.accounts.findOne(
					{
						where: { id: ctx.data.account },
						includeDeleted: true,
					},
					ctx,
				);
				if (!account || account.status !== "active" || account.deletedAt) {
					throw new Error("Account is unavailable");
				}
			},
		},
	});
```

The context discriminates `operation` (`create | update | delete | restore`)
and generated `method` (`create`, `updateById`, `updateMany`, `updateBatch`,
`deleteById`, `deleteMany`, or `restoreById`). `original` is the singular fresh
preimage when exactly one row was claimed; `originals` always contains all
fresh canonical claimed documents, including localization, collapsed
polymorphic values, virtual fields, and `_title`, without running output or
`afterRead` hooks. Treat `data` and the preimages as readonly facts. An
`updateBatch` invokes one batch-wide guard before any item writes; its
method-narrowed `data` is the caller-ordered readonly `{ id, data }[]` of
heterogeneous validated updates, and `originals`, `recordIds`, `records`, and
`count` cover the complete batch. Hook data keeps public logical field shapes;
for example, a polymorphic relation remains `{ type, id }`. Physical
discriminator/id columns are generated only in the separate persistence copy.

The object form separates declaration from decision. Every `locks` selector is
synchronous and receives the same typed readonly context as `run`. QUESTPIE
collects requests from the complete composed hook chain, coalesces aliases,
deduplicates at most 100 physical row identities, and claims each physical table
once in one shared UTF-8/type-tagged order. Only then does it execute every
`run` callback in hook-chain order. A guard needing no dependent rows may keep
the plain function form: `beforeWrite: ({ data }) => { ... }`.

Read dependent facts in `run` through the normal generated
`collections.<name>` API. Those reads inherit the exact transaction, stay
collection-key and field typed, and re-evaluate normal read access after any
lock wait. Pass the complete hook `ctx` to nested CRUD so the read keeps the
owning transaction, identity, locale, and access mode; do not open a sibling
connection while the guard holds row locks. A
missing, soft-deleted, or row-filtered document remains the ordinary
`null`/absent read result. A collection-level denial remains the ordinary `403`,
independent of whether a requested row exists. There is no parallel untyped
`facts` result or consumer cast.

Primary mutation rows are claimed before dependent rows. The helper removes
deadlocks caused only by callers supplying dependent collections or ids in
opposite orders. It cannot linearize a cyclic aggregate graph where one
mutation owns a primary row in collection A and then locks B while another owns
a primary row in B and then locks A; PostgreSQL aborts one participant and the
complete mutation rolls back. Model cross-collection guard dependencies as an
acyclic aggregate lock graph, and retry database deadlock/serialization errors
at the command boundary when concurrent commands can still form a cycle.

### What each stage is for

- **`beforeOperation`**, runs first for **every** operation, including read, delete, and purge. Use for logging, rate limiting, or early checks. `ctx.data` is the input (type depends on the operation), `ctx.original` is not available.
- **`beforeValidate`**, transform, normalize, and default the **mutable** input before the Zod schema runs. Mutate `ctx.data` in place. Create and update only.
- **`beforeChange`**, business logic on **validated** input: slug generation, derived fields, complex cross-field validation. The last point at which you can change what gets written. Create and update only; `ctx.original` is _not_ available here, diff in `afterChange` instead.
- **`beforeWrite`**, revalidate related durable facts after fresh primary-row claims. Declare dependent ids synchronously in `locks`, then read exact typed facts through `ctx.collections` in `run`. The input is deeply readonly and rejection rolls back the complete generated mutation.
- **`afterChange`**, react to a completed write with the full record. Has `ctx.original` on update for diffing. Runs **inside** the transaction, defer durable side effects with [`onAfterCommit`](#side-effects-onaftercommit).
- **`beforeRead`**, modify query options / add filters. Here `ctx.data` is the query context, not a row.
- **`afterRead`**, transform output, add computed fields, format values. Fires after create, update, delete, and read.
- **`beforeDelete`**, block deletion (throw), cascade, or back up. `ctx.data` is the record about to be deleted.
- **`afterDelete`**, transaction-bound cleanup and durable facts. `ctx.data` is the deleted record; throwing rolls back soft or hard delete.
- **`beforePurge`**, guard permanent removal of an already soft-deleted record. `data` and `original` are the same locked, localized persisted preimage before field-output/`afterRead` hooks. Throwing rolls back the purge.
- **`afterPurge`**, record transactional cleanup intents or facts. It receives the same preimage even though the owner row has been removed inside the transaction. Throwing rolls back the purge. Use `onAfterCommit` only for non-transactional side effects; durable external cleanup needs a transactional outbox. See [Soft delete and durable retention](/docs/concepts/soft-delete-retention).

### The hook context (`ctx`)

Every hook receives one argument, the `HookContext`. It is your `AppContext` (all framework services) plus the per-operation lifecycle fields. Destructure what you need:

```ts
type HookContext = AppContext & {
	data: TData; // see the stage table for what this is
	original: TOriginal; // update preimage, deleted row, or purge preimage depending on the stage
	operation: "create" | "update" | "delete" | "purge" | "read";
	locale?: string;
	accessMode?: "user" | "system";
	onAfterCommit: (callback: () => Promise<void>) => void;

	// Bulk metadata, present only inside updateMany / deleteMany:
	isBatch?: boolean;
	recordIds?: (string | number)[];
	records?: TData[];
	count?: number;
};
```

| `ctx` property                                          | What you get                                                                                                                                                       |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `data`                                                  | The lifecycle payload for this stage (input for `before*`; the record for `afterChange` / `afterRead` / delete hooks).                                             |
| `original`                                              | Update preimage on `afterChange` / `afterRead`; the same deleted row on `afterDelete`; the same locked persisted preimage on purge hooks; `never` on other stages. |
| `operation`                                             | `"create"` \| `"update"` \| `"delete"` \| `"purge"` \| `"read"`, narrowed per stage.                                                                               |
| `locale`                                                | The active locale for this operation, when set.                                                                                                                    |
| `accessMode`                                            | `"user"` (normal) or `"system"` (internal/seed/job code, bypasses access control).                                                                                 |
| `onAfterCommit`                                         | Queue a callback to run after the outermost transaction commits. See [Side effects](#side-effects-onaftercommit).                                                  |
| `db`, `collections`, `globals`                          | Database handle and typed access to other collections/globals.                                                                                                     |
| `queue`, `email`, `search`, `realtime`, `kv`, `storage` | Adapter services: queue jobs, email, search index, realtime, KV, file storage.                                                                                     |
| `session`, `services`, `logger`                         | The current session, your registered services, and the logger.                                                                                                     |
| `isBatch`, `recordIds`, `records`, `count`              | Bulk metadata, present only in `updateMany` / `deleteMany`. See [Bulk operations](#bulk-operations).                                                               |

`AppContext` is assembled from your registered adapters and services, so `ctx.session` and `ctx.services` are typed by your app's codegen. The same flat service surface is injected into access rules, routes, and jobs, once you know it in a hook, you know it everywhere.

<Callout type="info">
	**The email service is `ctx.email`, and you send with `sendTemplate`.** Reach
	for `ctx.email.sendTemplate({ template, input, to })`; `template` is one of
	your generated email keys and `input` is its typed props.
</Callout>

## Advanced

### Side effects (`onAfterCommit`)

`afterChange`, `afterDelete`, `afterPurge`, and `afterTransition` run **inside**
the CRUD transaction.
`queue.<job>.publish()` is transaction-aware: call and await it directly so
pg-boss joins the transaction or the framework commits an external-adapter
dispatch intent with the data. Direct email, HTTP calls, and other
non-transactional effects must still wait until commit. (`afterRead` runs
_after_ the transaction closes.) `afterTransition` retains its existing
non-fatal compatibility behavior; use `beforeTransition` to veto a transition.

Use `ctx.onAfterCommit(cb)` to defer only those non-transactional side effects until the **outermost** transaction commits:

```ts title="src/questpie/server/collections/posts.ts"
.hooks({
	afterChange: async ({ data, operation, onAfterCommit, queue, search }) => {
		if (operation === "create") {
			await queue.welcomePost.publish(
				{ postId: data.id },
				{ idempotencyKey: `welcome-post:${data.id}` },
			);
		}
		onAfterCommit(async () => {
			await search.scheduleIndex("posts", String(data.id));
		});
	},
})
```

- The callback runs **only after** the data is durably committed.
- If you call `onAfterCommit` **outside** any transaction, the callback runs **immediately** (fire-and-forget).
- Inside a managed transaction, callbacks run sequentially after commit and the
  operation waits for them, but their errors are logged and never propagated
  because the database commit is already final. Outside a transaction they run
  immediately as fire-and-forget work. Do not rely on either form to fail or
  roll back the request.

This is exactly how the framework's own realtime and search hooks are written, both subscribe to `afterChange` / `afterDelete` and wrap their broadcast/indexing in `ctx.onAfterCommit`, so events fire only on durable data.

<Callout type="warn">
	**Keep direct external effects out of an `after*` hook.** Transactional
	database writes through `ctx.db`, transaction-aware Queue publication, and
	typed Channels ledger writes intentionally commit or roll back with the
	operation. Direct email, HTTP, `realtime.notify`, or an independent database
	connection cannot join that transaction; put them in a durable job or
	`onAfterCommit`.
</Callout>

### Aborting an operation

Throw inside a rollback-capable mutation hook to abort. `before*`,
`afterChange`, `afterDelete`, and purge-hook errors **propagate** and roll the
operation back:

```ts title="src/questpie/server/collections/posts.ts"
import { ApiError } from "questpie/errors";

.hooks({
	beforeDelete: ({ data }) => {
		if (data.isProtected) {
			throw ApiError.badRequest("This record cannot be deleted.");
		}
	},
})
```

`ApiError` gives you a typed, status-mapped failure (`badRequest` → 400, `forbidden` → 403, `notFound` → 404, …) that serializes cleanly to the client. A plain `throw new Error(...)` also aborts, but is reported as a generic internal error (HTTP 500) rather than a typed one, so prefer `ApiError`. See [Validation](#related) for the full `ApiError` surface.

<Callout type="warn">
	**`afterRead` is not a rollback hook.** It runs after a write transaction has
	committed. A thrown error still rejects the caller's response, but it cannot
	undo data that already landed. Work that must never affect the response
	belongs in a durable job or [`onAfterCommit`](#side-effects-onaftercommit),
	whose callbacks are non-fatal because the commit is already final.
</Callout>

### Bulk operations

`updateMany` and `deleteMany` run hooks **per record** and attach batch metadata to `ctx`, so you can short-circuit expensive per-row work and reason about the whole batch:

```ts title="src/questpie/server/collections/posts.ts"
.hooks({
	afterChange: async ({ data, isBatch, recordIds, count, queue }) => {
		if (isBatch) {
			// This hook still fires once per affected record;
			// recordIds / count describe the whole batch.
		}
		await queue.reindexPost.publish(
			{ id: data.id },
			{ idempotencyKey: `reindex-post:${data.id}` },
		);
	},
})
```

- `isBatch` is `true` when the hook runs as part of `updateMany` / `deleteMany`.
- `recordIds` / `records` / `count` describe the whole batch. `records` semantics: **post-image** on update, **pre-image** on delete.
- Transaction-bound hook chains run sequentially in winner order. Any failure rolls back the complete bulk mutation.

<Callout type="warn">
	**Bulk `before*` hooks are *intent*, bulk `afterChange` is *fact*.** In a
	conditional (`where`-based) `updateMany`, `beforeValidate` and `beforeChange`
	run on the *pre-image* of every candidate row, they may fire for rows that
	then lose a concurrent write-time claim and are never actually written.
	`afterChange` (and the returned records) fire for the **winners only**. So put
	validation/transform that's safe to run speculatively in `before*`, and
	anything that must reflect a real committed change in `afterChange`.
</Callout>

### Transition hooks

With versioning and workflow enabled, `beforeTransition` and `afterTransition` fire around `transitionStage`. Their context describes the stage move with transition-specific fields:

```ts title="src/questpie/server/collections/posts.ts"
.hooks({
	beforeTransition: ({ data, fromStage, toStage, recordId }) => {
		if (toStage === "published" && !data.publishedAt) {
			throw new Error("Set publishedAt before publishing.");
		}
	},
	afterTransition: async ({ data, fromStage, toStage, queue }) => {
		await queue.announce.publish(
			{ postId: data.id, stage: toStage },
			{ idempotencyKey: `announce:${data.id}:${toStage}` },
		);
	},
})
```

The transition context carries `data` (the record), `recordId`, `fromStage`, `toStage`, an optional `scheduledAt` (set when the transition is scheduled for a future date instead of running now), `locale`, and `accessMode`, plus the usual `AppContext` services and `onAfterCommit`. Throw in `beforeTransition` to abort the transition.

### Arrays and composition

Any stage accepts a **single function or an array**, both are valid:

```ts
.hooks({
	beforeChange: [normalizeTitle, computeSlug, stampUpdatedBy],
})
```

Because `.hooks()` **merges** per stage, you can split hooks across calls or contribute them from modules, and they all run in registration order:

```ts
collection("posts")
	.hooks({ beforeChange: normalizeTitle }) // e.g. module A
	.hooks({ beforeChange: computeSlug }); // e.g. module B
// → both run on every change, in order
```

### Field access vs hooks

To strip or hide a single field by permission, prefer **field access rules** (`access.fields`) or `f.text().inputFalse()` (read-only, drop it from input) / `f.text().outputFalse()` (write-only, drop it from output) over writing a hook that deletes keys, they fold into the same authorization layer and run automatically. Use **hooks for logic** (deriving, reacting, side effects); use **access for authorization**. See [Access control](#related).

## TypeScript

Hooks are fully typed from your collection definition, `ctx.data`, `ctx.original`, and `ctx.operation` narrow per stage with **no annotations** when you write the hook **inline** on `.hooks({ ... })`.

For **shared helpers** in separate files, import the generated `HookRuleContext<K>` alias from `#questpie`, which narrows `data` to that collection's row:

```ts title="src/questpie/server/lib/post-hooks.ts"
import type { HookRuleContext } from "#questpie";

export function stampSlug(ctx: HookRuleContext<"posts">) {
	if (ctx.operation === "create" && ctx.data.title && !ctx.data.slug) {
		ctx.data.slug = ctx.data.title.toLowerCase().replace(/\s+/g, "-");
	}
}
```

`HookRuleContext<K>` is generated into `src/questpie/server/.generated/index.ts` and aliases the package-level `HookContext`, resolving `data` to `CollectionDoc<K>` and typing `ctx.session` / `ctx.collections` through your app's `AppContext`.

<Callout type="warn">
	**Cycle rule for the generated context aliases.** Import `HookRuleContext` /
	`AccessRuleContext` **only** from files that are *not* imported by a
	collection (routes, services, jobs, scripts). A helper that a collection
	imports must take the package-level `HookContext` / `AccessContext` from
	`questpie` instead, importing the generated `#questpie` barrel from a
	collection creates a codegen cycle.
</Callout>

The raw types live in the `questpie` package if you need them directly:

```ts
import type { HookContext, HookFunction } from "questpie";
// HookContext<TData, TOriginal, TOperation>
// HookFunction<TData, TOriginal, TOperation> = (ctx) => Promise<void> | void
```

- **[Globals](/docs/concepts/globals)**, singletons with their own `beforeUpdate` / `afterUpdate` hook stages.
- **[Jobs](/docs/concepts/jobs)**, whose typed `queue.*.publish()` joins the ambient hook transaction.
