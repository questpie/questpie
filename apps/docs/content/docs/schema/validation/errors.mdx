Your collection rejected a write. This page is what the caller sees, how the
typed client reads it, and how you raise a failure of your own.

## The body

A failed collection input parse or route input-schema parse becomes an `ApiError`
with code `VALIDATION_ERROR`, which maps to HTTP 400. The response wraps it under an `error` key:

```json
{
	"error": {
		"code": "VALIDATION_ERROR",
		"message": "Validation failed",
		"fieldErrors": [
			{
				"path": "settings.theme",
				"message": "Invalid option: expected one of \"light\"|\"dark\""
			}
		]
	}
}
```

| Key           | What it holds                                                                     |
| ------------- | --------------------------------------------------------------------------------- |
| `code`        | `VALIDATION_ERROR` from a schema parse, `BAD_REQUEST` from `ApiError.badRequest`. |
| `message`     | A summary line. QUESTPIE translates it when the error carries a translation key.  |
| `fieldErrors` | Up to eight entries, each with a dotted `path` and its own `message`.             |

Public responses omit causes, stack traces, invalid values, and database or hook
diagnostics in every environment. Internal and hook failures use the generic
`INTERNAL_SERVER_ERROR` code and message; log the original error server-side for
diagnostics. Only app-authored safe context is eligible for a public error.

A `ZodError` thrown by a route handler or its output validation is an internal
server failure (HTTP 500), rather than a client input error. When parsing client
input yourself, explicitly throw `ApiError.fromZodError(error)` for input
validation failures. Do not apply that conversion to output validation.

Nothing is written when the parse fails. No row, no `beforeChange`, no
`afterChange`.

## Reading it in the client

The typed client throws `QuestpieClientError` on any non-2xx response and parses
the envelope for you.

```ts
import { QuestpieClientError } from "questpie/client";

try {
	await client.collections.product.create({ name: "Chair", sku: "sku-1" });
} catch (error) {
	if (
		error instanceof QuestpieClientError &&
		error.isCode("VALIDATION_ERROR")
	) {
		error.getFieldError("sku"); // { path: "sku", message: "Use SKU-000000" }
		error.getFieldErrorsMap(); // { sku: ["Use SKU-000000"] }
	}
}
```

The admin form does the same thing and sets each message on its own input, so a
rule you wrote in the collection file shows up under the right control with no
extra work.

## Rules a field schema cannot see

A field schema sees one field. When the rule spans two, put it in
`beforeChange` and throw `ApiError.badRequest`. It carries the same
`fieldErrors` shape and the same HTTP 400.

```ts title="src/questpie/server/collections/booking.ts"
import { collection } from "#questpie/factories";
import { ApiError } from "questpie/errors";

export default collection("booking")
	.fields(({ f }) => ({
		startsAt: f.datetime().required(),
		endsAt: f.datetime().required(),
	}))
	.hooks({
		beforeChange: ({ data }) => {
			if (data.startsAt && data.endsAt && data.endsAt <= data.startsAt) {
				throw ApiError.badRequest("End must be after start", [
					{ path: "endsAt", message: "Must be after startsAt" },
				]);
			}
		},
	})
	.title(({ f }) => f.startsAt);
```

The caller now gets `code: "BAD_REQUEST"` and a `fieldErrors` entry pointing at
`endsAt`, which the admin renders under that input like any other failure.

<Callout type="info" title="Guard the fields you compare">
	`beforeChange` runs on updates too, where a patch may carry one date and not
	the other. Check both are present before comparing them.
</Callout>
