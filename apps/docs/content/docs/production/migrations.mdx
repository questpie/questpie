title: Migrations in production
description: Applying schema changes as a deploy step, why autoMigrate is the wrong tool with more than one replica, and how to sequence a change so old and new code can run at once.
---

Migrations are generated by the CLI from your schema and committed to the repo.
They are an append-only ledger: never edit one that has been applied anywhere.

```bash
bun run migrate:generate   # diff schema -> new migration + snapshot
bun run migrate:status     # what is applied, what is pending
bun run migrate            # apply pending migrations
bun run migrate:down       # roll back the last one
```

## Apply as a deploy step, not on boot

`build({ autoMigrate: true })` exists and is convenient in development. **Do not
use it in production with more than one replica.**

Each migration runs inside its own transaction, but there is **no advisory lock
around the runner**. Two instances booting at the same time can both see the same
pending migration and both try to apply it. What happens next depends on the
migration: a `CREATE TABLE` fails the loser cleanly, but a data backfill can run
twice.

Run migrations as their own step, once, before the new version starts serving:

```yaml title="Kubernetes"
# A Job that must complete before the Deployment rolls
apiVersion: batch/v1
kind: Job
metadata:
  name: migrate
spec:
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: migrate
          image: my-app:${VERSION}
          command: ["bun", "run", "migrate"]
          envFrom: [{ secretRef: { name: app-env } }]
```

Most platforms have an equivalent: a release command, a pre-deploy hook, or a
one-off task. Use it.

## Zero-downtime changes

During a rolling deploy, **old and new code run against the same database at the
same time**. A migration that only the new code can tolerate will break the old
replicas that are still serving.

The rule: every migration must be compatible with the code already running.

**Adding a column** is safe if it is nullable or has a default. Old code ignores
it.

**Adding a required column** is not one migration, it is three deploys:

1. Add the column as nullable. Deploy.
2. Backfill it, and ship code that writes it. Deploy.
3. Add the `NOT NULL` constraint. Deploy.

**Removing a column** is the same in reverse: stop reading it and deploy, then
drop it in a later deploy. Dropping while old replicas still `SELECT` it fails
their queries.

**Renaming** is never a rename in production. Add the new column, write both,
backfill, switch reads, then drop the old one.

**Long backfills do not belong in a migration.** A migration holds a transaction;
a backfill over millions of rows holds it for minutes and blocks everything else.
Write the schema change as a migration and the backfill as a job that processes
in bounded batches.

## Soft delete and purge

Soft-deleted rows stay in the table. `purgeById` removes one permanently, is
separately authorized, and is default-deny: delete authority does not grant it.

There is deliberately no `purgeMany`. For a retention backlog, use bounded keyset
batches in a scheduled job rather than one unbounded statement, so the work is
interruptible and does not hold a long transaction.

## Rollback

`migrate:down` reverses the last migration using its `down` step. It is a real
option for a schema change, but note what it cannot do: **a down migration cannot
restore data that an `up` deleted**. If a migration drops a column, rolling back
recreates the column, empty.

For anything destructive, take a backup immediately before applying and treat
restore, not rollback, as the recovery path.

## Verifying before you deploy

CI proves that a second generation produces no diff, so a committed migration
matches the schema it claims to. Locally:

```bash
bun run migrate:generate   # should produce nothing on a clean tree
bun run migrate:status     # should list your new migration as pending
```

If `migrate:generate` produces a second migration immediately after the first,
the schema and the migration disagree, and the deploy will not do what you think.
