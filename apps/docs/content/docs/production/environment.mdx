---
title: Environment
description: Schema-declared, boot-validated environment variables with typed server and client access.
---

QUESTPIE has a first-class env primitive: declare your environment variables once with a Standard Schema validator (zod, valibot, arktype), and the framework validates them **at boot — before adapters, auth, or the database initialize** — and gives you typed access everywhere. Client-safe vars are emitted by codegen as per-bundler modules where server keys are physically absent.

## Server: `env.ts`

Create `env.ts` next to `questpie.config.ts`. It default-exports the result of `env()`, which validates at module evaluation:

```ts title="src/questpie/server/env.ts"
import { env } from "questpie/env";
import { z } from "zod";

export default env({
	server: {
		DATABASE_URL: z.url(), // tightens the optional base var
		BETTER_AUTH_SECRET: z.string().min(32),
		STRIPE_SECRET_KEY: z.string().startsWith("sk_").optional(),
	},
	refine: (e) => {
		if (e.NODE_ENV === "production" && e.BETTER_AUTH_SECRET === "dev-secret")
			return "BETTER_AUTH_SECRET must not be the dev default in production";
	},
});
```

Consume it wherever you need typed env access — starting with `questpie.config.ts`:

```ts title="src/questpie/server/questpie.config.ts"
import { runtimeConfig } from "questpie/app";

import env from "./env";

export default runtimeConfig({
	db: { url: env.DATABASE_URL },
	secret: env.BETTER_AUTH_SECRET,
});
```

`env.DATABASE_URL` is `string` (you declared it required), `env.STRIPE_SECRET_KEY` is `string | undefined`. No hand-written types, no `process.env.X!` assertions.

### Boot order guarantee

Codegen emits `import "../env"` as the first app import in `.generated/index.ts` — before the runtime config. A misconfigured environment therefore fails the process before `runtimeConfig()` resolution, before adapters and auth initialize, and before any database connection is attempted.

Validation failures aggregate into a single error listing every offending **name** — values are never logged:

```txt
[questpie/env] Invalid environment:
  ✖ DATABASE_URL: Invalid URL
  ✖ BETTER_AUTH_SECRET: Too small: expected string to have >=32 characters
```

The validated object is also available as `app.env` (typed) on the app instance, and re-exported as `env` from `#questpie`.

### Framework base preset

The framework merges its own var declarations *under* your schema — your keys always win. Base vars are optional typed strings (presence is enforced by the runtime resolvers, since QUESTPIE Cloud injects `QUESTPIE_*` while self-hosting uses the standard names):

| Base var                                              | Type                                                |
| ----------------------------------------------------- | --------------------------------------------------- |
| `NODE_ENV`                                            | `"development" \| "test" \| "production"` (optional) |
| `QUESTPIE_DB`, `DATABASE_URL`                         | `string` (optional)                                  |
| `QUESTPIE_APP_URL`, `APP_URL`                         | `string` (optional)                                  |
| `QUESTPIE_SECRET`, `BETTER_AUTH_SECRET`               | `string` (optional)                                  |
| `QUESTPIE_STORAGE_ENDPOINT`, `QUESTPIE_STORAGE_BUCKET`, `QUESTPIE_STORAGE_REGION`, `QUESTPIE_STORAGE_ACCESS_KEY`, `QUESTPIE_STORAGE_SECRET_KEY` | `string` (optional) |

Re-declare any base var in your `server` block to tighten it — `DATABASE_URL: z.url()` turns the optional base var into a boot requirement.

### Options

| Option                   | Default                                          | Description                                                              |
| ------------------------ | ------------------------------------------------ | ------------------------------------------------------------------------ |
| `server`                 | —                                                | Server-only vars. Client-prefixed keys (`VITE_*`, `EXPO_PUBLIC_*`, `NEXT_PUBLIC_*`, `PUBLIC_*`) are a compile error. |
| `client`                 | `undefined`                                      | The `env.client.ts` definition (see below).                              |
| `refine`                 | `undefined`                                      | Cross-field guard run after per-var validation. Return or throw a message to fail boot. |
| `emptyStringAsUndefined` | `true`                                           | Treat `""` as unset before validation.                                   |
| `skipValidation`         | `Boolean(process.env.QUESTPIE_SKIP_ENV_VALIDATION)` | Skip validation entirely (raw reads). Codegen sets the flag automatically. |
| `isServer`               | runtime detection                                | `env.ts` is server-only; importing it in a browser context throws.       |

### Env-less builds

`questpie generate` and `questpie dev` set `QUESTPIE_SKIP_ENV_VALIDATION=1` before importing your config — codegen never requires a populated environment. Use the same flag for Docker build stages and CI typecheck steps that import server code without real secrets:

```dockerfile
RUN QUESTPIE_SKIP_ENV_VALIDATION=1 bunx questpie generate
```

## Client: `env.client.ts`

Bundlers only inline env vars referenced as **literal member expressions** (`process.env.EXPO_PUBLIC_X`, `import.meta.env.VITE_X`). QUESTPIE turns that constraint into codegen: declare client-safe vars once, with unprefixed logical names, and declare which bundlers consume them:

```ts title="src/questpie/server/env.client.ts"
import { clientEnv } from "questpie/env";
import { z } from "zod";

export default clientEnv({
	consumers: ["expo", "vite"],
	vars: {
		APP_URL: z.url(),
		POSTHOG_KEY: z.string().optional(),
	},
});
```

Pass it to `env()` so the server validates client vars too — under the unprefixed name, with a prefixed fallback per consumer (`APP_URL ?? EXPO_PUBLIC_APP_URL ?? VITE_APP_URL`). A single `.env` file works for both sides:

```ts title="src/questpie/server/env.ts"
import { env } from "questpie/env";
import { z } from "zod";

import client from "./env.client";

export default env({
	client,
	server: {
		DATABASE_URL: z.url(),
	},
});
```

### Generated client modules

`questpie generate` emits one module per consumer into `.generated/`:

```ts title=".generated/env.client.vite.ts (generated)"
import _envClient from "../env.client";
import { resolveClientEnv } from "questpie/env-client";

export const env = resolveClientEnv(_envClient, {
	APP_URL: import.meta.env.VITE_APP_URL,
	POSTHOG_KEY: import.meta.env.VITE_POSTHOG_KEY,
}, "vite");
export type ClientEnv = typeof env;
```

Every var is a literal prefixed reference the bundler can inline, and server keys never appear — by construction, not by tree-shaking. Import it from client code:

```ts title="src/lib/client.ts"
import { env } from "#questpie/env.client.vite";

env.APP_URL; // string — validated at module import
// @ts-expect-error — server keys do not exist on this module
env.DATABASE_URL;
```

Built-in consumers:

| Consumer | Prefix         | Inlined expression           |
| -------- | -------------- | ---------------------------- |
| `expo`   | `EXPO_PUBLIC_` | `process.env.EXPO_PUBLIC_X`  |
| `vite`   | `VITE_`        | `import.meta.env.VITE_X`     |
| `next`   | `NEXT_PUBLIC_` | `process.env.NEXT_PUBLIC_X`  |

Custom bundlers take an explicit config: `{ name: "astro", prefix: "PUBLIC_", envObject: "import.meta.env" }`.

### Exposing client env to other apps

In a monorepo where frontend apps consume your API package, add a one-time export glob to the API package's `package.json`:

```json title="apps/api/package.json"
{
	"exports": {
		"./env/*": "./src/questpie/server/.generated/env.client.*.ts"
	}
}
```

The Expo app then imports its typed env without hand-writing anything:

```ts
import { env } from "@acme/api/env/expo";

env.APP_URL; // string (from EXPO_PUBLIC_APP_URL, validated at import)
```
