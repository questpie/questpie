---
title: Trace a slow request
description: Wire OpenTelemetry into a QUESTPIE app, run a collector locally, and read the waterfall down to the SQL statement that was actually slow.
---

The point of tracing is not that spans exist. It is that when someone says "the
orders page is slow", you can answer with a query and a number instead of a
guess. This recipe gets you from nothing to that answer.

## 1. Install and configure

```bash
bun add @questpie/observability
```

```ts title="src/questpie/server/questpie.config.ts"
import { otelObservability } from "@questpie/observability";
import { runtimeConfig } from "questpie/app";

export default runtimeConfig({
	// ...db, storage, email
	observability: {
		adapter: otelObservability({
			serviceName: "my-app",
			environment: process.env.NODE_ENV,
			otlpEndpoint: process.env.OTLP_ENDPOINT,
		}),
	},
});
```

Without `otlpEndpoint` nothing is exported and every seam still calls straight
through, so it is safe to leave this in place in development.

## 2. Run a collector

Jaeger is the shortest path to a waterfall you can actually look at:

```bash
docker run --rm -p 16686:16686 -p 4318:4318 jaegertracing/all-in-one:latest
```

```bash title=".env"
OTLP_ENDPOINT=http://localhost:4318
```

Start the app, make a request, then open `http://localhost:16686` and pick your
service.

## 3. Read the waterfall

A single `GET /orders` looks roughly like this:

```
GET /orders                          142ms   server
└─ collection.find                   138ms   internal   db.collection.name=orders
   ├─ db.select                        4ms   client     db.sql.table=orders
   └─ db.select                      131ms   client     db.sql.table=order_items
```

That last line is the answer. The route is not slow, the collection operation is
not slow. One query against `order_items` is, and `db.statement` on that span
carries the SQL to take to `EXPLAIN`.

Nesting is what makes this readable, and it is real parent/child linkage rather
than a shared trace id. Spans inside a `db.transaction()` appear under it, which
is usually where the surprise is on writes.

## 4. Correlate the logs

Every log line written during that request carries `trace_id` and `span_id`. In
any backend that ingests both, paste the trace id from Jaeger into your log
query and you get exactly the lines from that request, including the ones from
inside the slow query's span.

```ts
export default route()
	.get()
	.handler(async ({ logger, collections }) => {
		const orders = await collections.orders.find({ limit: 50 });
		// Carries trace_id/span_id automatically; nothing to thread through.
		logger.info("orders listed", { count: orders.docs.length });
		return orders;
	});
```

## 5. Add your own span where the framework cannot see

The framework instruments its own seams. Anything you call yourself, a payment
provider or an image pipeline, is invisible until you say so:

```ts
const rates = await ctx.app.observability.span(
	"stripe.list_prices",
	async () => stripe.prices.list({ limit: 100 }),
	{ kind: "client", attributes: { "payment.provider": "stripe" } },
);
```

It nests under whatever is active, so it lands in the same waterfall.

## 6. Before you ship it

**Sample.** Tracing every request in production is expensive and rarely more
informative than tracing a tenth of them:

```ts
otelObservability({ serviceName: "my-app", samplingRatio: 0.1 });
```

The sampler is parent-based, so a request that arrived already sampled stays
sampled regardless of the ratio. Otherwise you get partial traces that break at
your service, which is worse than no trace.

**Shut down.** Spans are batched. A process that exits without flushing loses
the last batch, which is disproportionately the interesting one because it
contains whatever happened just before the crash:

```ts
process.on("SIGTERM", async () => {
	await app.observability.shutdown();
});
```

**Know what is missing.** Search query text, KV keys, record contents and SQL
parameters are deliberately never attached: a tracing backend is searchable,
long-lived and widely readable inside a company. If an investigation needs one
of them, add it on your own span where the decision is explicit and scoped.

## Distributed setups

An inbound `traceparent` header is continued rather than replaced, so a request
arriving from another service joins that trace with the caller's span as parent.
You do not have to do anything for this; it is the default. What you _do_ have to
do is propagate outward on calls you make yourself, if you want the far side to
join too.
