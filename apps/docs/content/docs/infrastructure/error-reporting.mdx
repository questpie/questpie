Tracing tells you how requests behave. Error reporting tells you that one
failed and where. QUESTPIE keeps the two separate. A span records every failure
in every enclosing span, is sampled, and carries the error message as its
status. An incident report needs the opposite: exactly one report per failure,
whether or not tracing is on, with nothing in it the framework cannot vouch for.

## What the framework reports

With an adapter configured, the framework reports these failures itself. You
do not wrap routes or jobs.

| Where | Reported                                                           | Not reported                               |
| ----- | ------------------------------------------------------------------ | ------------------------------------------ |
| HTTP  | A thrown error that became a 5xx (`kind: "thrown"`)                | 4xx: validation, auth, not found, conflict |
|       | A 5xx the handler returned without throwing (`kind: "returned"`)   | Unmatched routes                           |
|       | A response body that failed after the status was sent (`"stream"`) | A body the client cancelled                |
| Queue | Every failed attempt, with `final: true` when no retry follows     | Attempts cancelled by worker shutdown      |

A returned 5xx has no original error, so the adapter receives `undefined`
rather than a made-up one. A secret-payload job only ever hands the reporter its
redacted, cause-free error.

Jobs are reported the same way from `app.queue.listen()` and
`app.queue.runOnce()`, once per failed attempt, so a job that is retried twice
and then fails produces three reports. A secret-payload job the broker delivers
again while another attempt still holds its dispatch is not reported: that
attempt reports its own outcome. What `final` and cancellation mean
depends on the queue adapter:

| Queue adapter     | `final`                              | Cancelled attempts, not reported |
| ----------------- | ------------------------------------ | -------------------------------- |
| pg-boss           | From the job's retry count and limit | None: there is no abort signal   |
| Graphile Worker   | From the dispatch's attempts         | Worker shutdown                  |
| BullMQ            | From `attemptsMade` and `attempts`   | None: there is no abort signal   |
| Cloudflare Queues | Omitted: the report has no `final`   | None: there is no abort signal   |

Without an abort signal an attempt runs to its outcome, and a failure is
reported even when the worker is stopping. With Graphile Worker an attempt that
runs past `expireInSeconds` is reported as a `QueueExecutionTimeoutError` the
moment the deadline passes, even if its handler ignores the signal and never
settles; whatever the attempt does afterwards is not reported again. When `listen()` handles
`SIGINT` or `SIGTERM` (its default graceful shutdown), pending reports are
delivered before the process exits, within the queue's `shutdownTimeoutMs`. If
you stop a worker yourself, call `app.destroy()`, which drains them.

Reporting never changes the outcome. `report()` is synchronous, never throws
and never awaits delivery. The response, the thrown error, the transaction and
the job's retry and ack decision are identical with or without an adapter, and
identical when the adapter throws, rejects or hangs.

## The contract

```ts
import type { ErrorReportingAdapter } from "questpie/errors";

const adapter: ErrorReportingAdapter = {
	report(error, report) {
		// error: the raw thrown value, which stays in your process
		// report: { source, kind?, method?, route?, status?, job?, final?, trace? }
	},
	flush: async (timeoutMs) => {},
	shutdown: async (timeoutMs) => {},
};
```

`report` is closed. `source` is `http`, `job`, `background`, `manual` or
`process`. `route` is the matched route template (`items/:id`), never the raw
path. `job` is the static job name, never a dispatch or idempotency id. Anything
else you pass is dropped before the adapter sees it. `trace` is added only when
an observability adapter has a span open at the time.

The framework always passes a template. When you pass `route` yourself, pass a
template too: a value with a URL scheme or host (`https://…`, `//…`) is dropped,
but a raw path such as `invite/abc123` has the same shape as a template and is
sent as it is.

Report your own failures from any handler:

```ts
export default route()
	.post()
	.handler(async ({ errors }) => {
		try {
			await syncInventory();
		} catch (error) {
			errors.report(error, { source: "background" });
		}
		return { ok: true };
	});
```

Within one HTTP request or one job attempt, the same error object is reported
once, so reporting it and then rethrowing does not produce a second event. The
same object failing another request, or the next retry, is a new occurrence and
is reported again. Outside a request or job, every call reports.

Delivery is bounded: at most `maxPending` (100) reports in flight, each released
after `timeoutMs` (5 s). `app.destroy()` drains what is pending and shuts the
adapter down within `shutdownTimeoutMs` (5 s).

## Sentry

```bash
bun add @questpie/sentry
```

`@questpie/sentry` needs Node 20.19+, 22.12+ or 23.2+, the same floor as the
Sentry 11 SDK it builds on. It has three entrypoints. The browser bundle does
not import Node code, and the server does not import browser or build code.

| Entrypoint                 | For                                         | Depends on                   |
| -------------------------- | ------------------------------------------- | ---------------------------- |
| `@questpie/sentry/server`  | HTTP, jobs and workers                      | `@sentry/core`               |
| `@questpie/sentry/browser` | Uncaught errors and router error boundaries | `@sentry/core`               |
| `@questpie/sentry/vite`    | Source map upload at build time             | `@sentry/vite-plugin` (peer) |

### Server and worker

```ts title="src/questpie/server/questpie.config.ts"
import { sentryErrorReporting } from "@questpie/sentry/server";
import { runtimeConfig } from "questpie/app";

export default runtimeConfig({
	errors: {
		adapter: sentryErrorReporting({
			dsn: process.env.SENTRY_DSN,
			release: process.env.RELEASE,
			environment: process.env.NODE_ENV,
			filenameRoot: process.cwd(),
		}),
	},
});
```

The HTTP server and a standalone `app.queue.listen()` worker read the same
config, so both report. Without `dsn`, `sentryErrorReporting()` returns
`undefined` and error reporting stays off with no per-request cost, so you can
wire it unconditionally and enable it per environment.

#### Uncaught exceptions and unhandled rejections

The framework reports failures inside requests and jobs. An error that escapes
everything and is about to end the process is not reported unless you opt in,
once per process, after the app is created:

```ts title="src/server.ts"
import { installProcessErrorHandlers } from "@questpie/sentry/server";

installProcessErrorHandlers(app.errors);
```

It reports the error with `source: "process"` and does not change how the
process ends. If no other `uncaughtException` listener is installed, it waits
for delivery up to `flushTimeoutMs` (2 s), then rethrows, so the runtime prints
the error and exits with the same code as before. The process keeps running in
its failed state during that wait, so keep the timeout short. If your app has
its own listener, that listener decides what happens and this only reports.

Node raises an unhandled rejection as an uncaught exception by default, so one
listener covers both; on Bun an `unhandledRejection` listener is added too.
With `--unhandled-rejections=warn`, `warn-with-error-code` or `none`, the
process keeps running after a rejection and rejections are not reported. The
returned function removes the listeners.

### Browser

```ts title="src/lib/error-reporter.ts"
import {
	createBrowserErrorReporter,
	installGlobalErrorHandlers,
} from "@questpie/sentry/browser";

export const errorReporter = createBrowserErrorReporter({
	dsn: import.meta.env.VITE_SENTRY_DSN,
	release: import.meta.env.VITE_RELEASE,
	environment: import.meta.env.MODE,
});

if (typeof window !== "undefined") {
	installGlobalErrorHandlers(errorReporter, window);
}
```

Report router error boundaries with the matched route **template**, so
`/invite/$token` is reported and the token is not:

```ts title="src/router.tsx"
import { createRouterErrorReporter } from "@questpie/sentry/browser";
import { createRouter } from "@tanstack/react-router";

import { errorReporter } from "./lib/error-reporter";

export function getRouter() {
	const router = createRouter({
		routeTree,
		defaultOnCatch: createRouterErrorReporter(
			errorReporter,
			() => router.state.matches.at(-1)?.routeId,
		),
	});
	return router;
}
```

`createRouterErrorReporter` returns a plain `(error) => void`, so it fits any
router's catch hook. The reporter caps itself at 30 events a minute so a render
loop cannot flood the project.

### Server-side rendering

With TanStack Start, an error thrown while the server renders a page, in a
loader or in a component, is reported once, by the browser. The router sends
the failed match with the page, and `defaultOnCatch` reports it when the page
hydrates. The server does not report it: QUESTPIE reports failures of its own
routes, not of page rendering, so there is no second report. A page whose
JavaScript never runs is therefore not reported.

This was checked in a production build with `@tanstack/react-start` 1.168.60
and `@tanstack/react-router` 1.170.41: a loader error and a render error, each
reached by a full page load and by client navigation, produced one report each.

### Why not `@sentry/tanstackstart-react`

Sentry's TanStack Start SDK is in beta. It initialises Sentry clients on the
server and in the browser and brings `@sentry/node`, `@sentry/react` and
`@opentelemetry/api`, so it adds the global client, default integrations and
OpenTelemetry setup this package leaves out. `@questpie/sentry` builds each
event from an allowlist on `@sentry/core` alone; a router error reaches it
through `createRouterErrorReporter` and an uncaught one through
`installGlobalErrorHandlers`, so the SDK is not needed.

### Upgrades

- `@questpie/sentry` pins `@sentry/core`, and its `@sentry/vite-plugin` peer,
  to one exact version. A Sentry upgrade arrives as a new `@questpie/sentry`
  release; install the plugin version it names.
- The router bridge relies only on the router calling `defaultOnCatch(error)`
  and on `routeId` being the route template. Check both again after a TanStack
  Router or Start upgrade.

### Source maps

```ts title="vite.config.ts"
import { questpieSentryVite } from "@questpie/sentry/vite";

export default defineConfig({
	plugins: [
		// ...your framework plugins
		questpieSentryVite({
			org: "my-org",
			project: "my-app",
			release: process.env.RELEASE!,
		}),
	],
});
```

The plugin injects debug ids into each bundle and uploads the maps with
`SENTRY_AUTH_TOKEN`. It sets `build.sourcemap` to `"hidden"` unless you set it,
so bundles do not reference their maps. After the build it deletes `**/*.map`
under the build output so your web server cannot serve them, whether or not
they were uploaded. Keep the token in a CI secret; it is a build credential and
never part of a bundle. Without a token, debug ids are still injected and
nothing is uploaded. To upload the maps in a later step instead, pass
`filesToDeleteAfterUpload: []` and delete them yourself once they are uploaded.

Use one `release` value for the build, the server and the browser. Events are
symbolicated by debug id, so a frame resolves only against maps from the same
build. The uploaded maps carry your browser source code, which Sentry stores
and shows next to each frame.

## What leaves the process

The Sentry adapter builds the event from an allowlist, and the event below is
the complete payload:

- `exception`: for the error and up to three causes, a type and stack frames.
  - The type is a built-in name (`TypeError`, `RangeError`, `AbortError`, …)
    or one you list in `errorNames`. Every other class is reported as `Error`:
    a name like `AcmeCustomerError` looks exactly like a safe one, so shape is
    not trusted.
  - Frames always carry line and column. A frame carries its file only when
    that file is a build artifact registered by `questpieSentryVite` (its
    debug id), or a server file you list exactly in `trustedFiles`, for a
    worker you run unbundled. Every other file is dropped, whatever its path:
    a script on another host, an inline script on `/invite/<token>`, a file
    under `uploads/`. A kept file is sent without host, credentials or query,
    as `app:///assets/index-Ab12.js` in the browser or, on the server,
    relative to `filenameRoot` (default `process.cwd()`) as
    `app:///dist/server.mjs`. `filenameRoot` only decides how a file is
    written, not whether it is sent; a filesystem or drive root (`/`, `C:\`)
    is not a root, so set it explicitly when the process runs from `/`. Paths
    with `.` or `..` segments are dropped.
  - Function names are not sent. Sentry restores them, with the original
    files, from your uploaded source maps, matched by debug id.
  - The value is a description built from `report`
    (`HTTP 500 POST items/:id (thrown)`), not the error message.
- `tags` and `transaction`: the validated `report` fields.
- `release`, `environment`, `platform`, `level`, `timestamp`, `event_id`.
- `contexts.trace`, only when a span was active.
- `debug_meta`, the debug ids needed for source maps.
- `sdk`: the reporter's name and version, and `settings.infer_ip: "never"`,
  which tells Sentry not to store the sender's IP as the user.
- `user`: only an empty `geo`. Sentry looks up a location from the sender's IP
  only when an event has none, so this keeps it from adding one.

Never sent: the error message, `cause` messages, custom error names you have
not listed, function names, local variables, source context lines, the request
(URL, headers, cookies, body, IP), the session or any user data, job payloads,
SQL, logs, breadcrumbs, spans, sessions and replays.

What is sent is still yours to judge. File paths under your app root and the
names you list in `errorNames` go out as they are, and the masking inside kept
paths is a pattern match, not a guarantee.

By default, inspecting a thrown value runs none of its code (no getter, proxy
trap, `toJSON` or `toString` of the error) and no stack-formatting hook, and
the reporter never modifies globals. Values that cannot be verified are
reported without frames:

- On the server, a value is inspected only after Node's own brand checks
  (`isNativeError`, `isProxy`), which a proxy cannot intercept. A proxy is
  reported as `NonError`, and so is a `DOMException` in Bun.
- In the browser, by default the thrown value is not inspected at all: every
  thrown object is reported as `Error` and each primitive as `NonError`,
  without frames, in every browser. The only browser brand check is
  `Error.isError`, and a polyfill of it (core-js
  ships one that reads `Symbol.toStringTag` and reports itself as native code)
  can run getters on the value. With `formattedStacks` (below) the value is
  inspected using the runtime's `Error.isError`, whatever it is; without one,
  every value is reported as `NonError`. Values that fail that check are
  also reported as `NonError`.
- Only the error's own properties are read. Its prototype is read only when it
  is a built-in error prototype, so a custom class reports its type only when
  it sets `name` on the instance (`this.name = "ApiError"` or a class field)
  and you list it in `errorNames`.
- With `formattedStacks` (below), a stack is formatted with a header built from
  `name`, `message` and, for Node's own errors, `code`. It is read only when
  those are plain data on the error itself or on built-in prototypes; on the
  server, also on custom prototypes that are verified not to be proxies.

### Reading stacks

Most runtimes produce an error's stack the first time it is read, by running
the runtime's stack formatter: in V8 and Bun that is whatever
`Error.prepareStackTrace` the error's realm has installed (Node's and Bun's
own defaults, a source-map hook such as `source-map-support`, or one of
yours), and which realm an error came from cannot be determined reliably. On
Node 20 and Bun even inspecting the `stack` property, without reading it,
formats the stack.

So by default stacks are not read. On Node 20 and Bun nothing about `stack` is
touched. On Node 22+, where inspecting it formats nothing, a `stack` that is
already a plain data property is read and anything else is left alone. In
browsers the value is not inspected at all by default (see above). In
practice, on Node, Bun and in every browser errors are reported without
frames, and therefore without source-mapped locations.

To get frames there, opt in explicitly:

```ts
sentryErrorReporting({ dsn, release, formattedStacks: true });
createBrowserErrorReporter({ dsn, release, formattedStacks: true });
```

This reads the stack exactly as `error.stack` does in your own logging, so the
"runs none of its code" guarantee above no longer covers stacks:

- Whatever formatter or `prepareStackTrace` accessor is installed runs, and it
  can run any code, including getters on the error and changes to globals. The
  reporter only keeps its own reads of `name`, `message` and `code` free of
  getters and proxies, and it never modifies globals itself.
- What a custom or source-mapping formatter puts into the stack is your
  responsibility. File locations still follow the rules above: only registered
  or listed files are sent.

Turn it on when every stack formatter in your process is one you are content
to have run while an error is being reported.

### Coexisting with OpenTelemetry

The adapter does not initialise a Sentry client. It registers no global scope,
no integrations, and no OpenTelemetry tracer provider, propagator or context
manager. An existing `@questpie/observability` setup, including a metrics-only
one, keeps working as before, and error reporting does not need tracing to be
on.

### What you still configure in Sentry

These live in your Sentry organisation, not in code:

- **IP addresses.** The event carries no IP, asks Sentry not to infer one
  and gives an empty location, so Sentry stores neither the sender's IP nor a
  location derived from it (checked on Sentry's EU region). Sentry still
  sees the connecting address of whoever sends it. Turn on the project's
  "Prevent Storing of IP Addresses" setting as a second layer; it does not by
  itself remove the location. To keep the browser's address away from
  Sentry entirely, pass `tunnel: "/monitoring"` and forward envelopes from
  your own server.
- **Alerts.** Who gets notified, and how, is an alert rule in the project.
- **Data scrubbing.** Server-side scrubbing is a useful second layer.
  It does not replace the allowlist.
